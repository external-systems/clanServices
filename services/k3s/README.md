# k3s

A thin [k3s](https://docs.k3s.io/) Kubernetes cluster service built on
`lib/kube-cluster`. It deploys an airgap-ready k3s control plane plus
Cilium (native routing over the `node_transport`, D72; kube-proxy replacement,
Node IPAM) and CoreDNS — with the initial cluster PKI pre-generated by
clan vars and a per-node haproxy kube-apiserver load balancer.

For the cross-distro architecture, current-versus-planned capability matrix,
networking invariants, and delivery plan, see [SPEC.md](../../SPEC.md).

## Roles

- `server` — runs the control plane and, by default, workloads.
- `agent` — worker node.

## Quick start

```nix
{
  instances = {
    # A one-machine fabric: routed-fabric is the only transport (D72),
    # and the cluster takes its node addresses from it.
    fabric = {
      module.name = "routed-fabric";
      module.input = "self";
      roles.spine.machines.alpha = {};
    };
    kube = {
      module.name = "k3s";
      module.input = "self";
      roles.server = {
        settings.network.fabric = {
          service = "routed-fabric";
          instance = "fabric";
        };
        machines.alpha.settings.clusterInit = true;
      };
    };
  };
}
```

A cluster always rides a fabric: its node addresses, links and MTU come
from the fabric's `node_transport` export (SPEC.md D72, D76). One machine
is a one-machine fabric, as above. `module.input = "self"` names the flake
that holds the services; use its input name in your clan. A nix-unit test
(`test_readmeQuickStart`) evaluates this inventory and expects no failed
assertion (H7).

`clusterInit = true` selects embedded etcd. Exactly one server per instance must
set it; joining servers and agents use `server` through their local haproxy.

## Node addressing

`settings.network.fabric` is required: the `routed-fabric` instance (or any
transport that implements the neutral `node_transport` schemaVersion 2,
D58) whose export gives every member its node addresses. The service never
branches on provider service names (SPEC.md D58). Every member must be in
that instance; a member without an export is an eval error. There are no
per-machine address options: manual addresses were removed in round 67
(D76).

## Who reaches what

The node firewall opens each port by source, from one matrix
(`lib/kube-cluster/firewall.nix`, SPEC.md §6.12). Every rule also needs a
fabric link or a local pod link; no link is trusted.

| Port | On | From |
|---|---|---|
| 6443 (API) | servers | members, the cluster's pods |
| 10250 (kubelet) | every node | servers; pods only with `firewall.kubeletFromPods = true` |
| 4240 (Cilium health) | every node | members |
| 2379, 2380 (etcd) | servers | servers |

The HAProxy fronts listen on loopback only, so no other host and no pod
reaches them. etcd's metrics port (2381) listens on loopback. A pod
reaches the API on a server and nothing else of a node. A metrics scraper
in a pod (metrics-server) needs `firewall.kubeletFromPods = true`.

## Exports

The service consumes `node_transport` (schemaVersion 2, D58) and
publishes `kube_cluster` per member
machine (SPEC.md §6.2): schema version, cluster identity (name, resolved
cilium id, resolved dual-stack pod/service CIDRs, clusterDNS), mesh group,
transport
source, per-member mesh endpoints with effective topology labels, and pool
handoff facts. Fleet-wide assertions (duplicate names/ids, meshed-CIDR overlap,
node-in-two-clusters incl. cross-distro, mesh-group transport consistency) are
computed from these exports as `clan.checks` by the shared lib's fleet-checks
module.

## The per-node haproxy kube-apiserver LB

Every node — servers AND agents — runs a local haproxy whose fronts listen
on loopback only (`127.0.0.1` and `::1`, D76):

- The kubeapi FQDN (`kubeapi-<instance>.<domain>`) resolves to loopback via
  `/etc/hosts`. Joining servers/agents, Cilium (its pods are host-network
  and read the node's `/etc/hosts`), and the admin kubeconfig all go
  through the local haproxy. Every member disables k3s's built-in agent
  client-side API LB so it keeps this path. No other host and no pod
  reaches a front.
- k3s serves its HTTPS/kube-apiserver endpoint on `6443`
  (`https-listen-port`). The only LB frontend is the derived kubeapi port
  `7442 + <resolved cilium id>` (explicit pin or hashed default, SPEC.md
  §6.2); there is no separate RKE2-style supervisor frontend.
  Join URLs and the admin kubeconfig use the derived LB port, while haproxy
  backends target `6443`.
- Backends are every server member's node addresses with TLS `/readyz`
  healthchecks. Every server line pins its source to this node's address
  (`source`), so the servers see a member. The check verifies the serving
  chain against the pre-generated server CA and presents a vars-issued
  client cert. A server lists itself plain and the remote servers
  `backup`; agents list all servers plain. `option allbackups` routes
  around dead backends.
- Loopback always exists, so haproxy starts before the fabric is up; a
  backend is DOWN until the fabric holds the node's address, then UP.
- The check also verifies that the certificate names the kubeapi FQDN
  (`verifyhost`).
- A read-only stats page on loopback (`127.0.0.1:8404`, `[::1]:8404`), with
  no password; the admin path is `/run/haproxy/haproxy.sock`.

## Vars bootstrap and CA lifecycle

`clan vars generate` pre-generates everything; nothing prompts:

- `rancher-pki-<instance>` (initializing server only) — the cluster CA tree and
  service-account key. A oneshot unit (`k3s-<instance>-pki-seed`) installs the CA
  material into `/var/lib/rancher/k3s/server/tls` before the first `k3s.service`
  start. It does not overwrite an initialized TLS tree and has no path watcher.
  Joining servers receive the cluster CA through k3s's normal bootstrap flow.
- `rancher-server-token-<instance>` (servers only) /
  `rancher-agent-token-<instance>` (every node) — join tokens. An agent joins
  with the agent token and never holds the server token.
- `rancher-clustermesh-ca-<group>` / `rancher-clustermesh-<instance>`
  (the `clusterInit` server only) — the ClusterMesh CA and leaf set; the
  secrets oneshot there is their one reader.
- `rancher-haproxy-<instance>` (every node) — the `/readyz` healthcheck client
  cert + CA chain.
- `rancher-admin-kubeconfig-<instance>` (servers only) — an operator client cert
  (CN=admin, O=system:masters, 365 days, random serial; renew with
  `clan vars generate --regenerate` on a branch) signed by the vars client CA; server URL is the
  kubeapi FQDN on the LB port. Linked to
  `/etc/rancher/k3s/admin-kubeconfig` on servers. k3s's native kubeconfig remains
  at `/etc/rancher/k3s/k3s.yaml`.

The datastore becomes authoritative after initialization. Rotate k3s CA
certificates with `k3s certificate rotate-ca`; do not regenerate vars to rotate
a live cluster's CA files.

## Cilium and CoreDNS

The service disables Flannel, k3s's network-policy controller, kube-proxy,
and (in the minimal base) the helm-controller. Cilium — plus the
`CiliumPodIPPool`, LB pools, and the clan CoreDNS serving `cluster.local`
(D46) — is
delivered by the kubenix bootstrap bundle, applied at boot and on each deploy that changes it via server-side
apply by a systemd oneshot on the `clusterInit` node (D40); nothing is
written to the k3s manifests dir. The bundle imports the artifact flake's
committed Cilium manifest and merges per-cluster variation (cluster
name/id, CIDRs, KPR endpoint, devices/MTU, Node IPAM) into the typed
resource tree — the chart is never re-run here (D26).

In the minimal base (`distroDefaults.enable = false`, the default, D42)
k3s's bundled CoreDNS is DISABLED (`--disable=coredns`) and the
clan-rendered CoreDNS serves `cluster.local` from the bundle; with
`distroDefaults.enable = true` the distro's stock CoreDNS deploys and the
bundle skips its own (D46, mode-exclusive). The clan Corefile imports the
`coredns-custom` ConfigMap per the k3s convention — but that ConfigMap is
OPTIONAL and GitOps-owned: clan NEVER renders it, and the deployment must
boot cleanly with it absent (D46). `coredns.rewrites` renders Corefile
rewrites into the clan CoreDNS, never the ConfigMap.
`coredns.helmValues` is rejected: k3s CoreDNS is not a Helm chart. No
member-facing private DNS service or VIP exists in either mode (D22,
day-2).

## distroDefaults

With `distroDefaults.enable = false` (the default, SPEC.md D42) the service
passes the k3s disable flags for the distro's packaged add-ons — Traefik,
local-storage, metrics-server — and disables the helm-controller, yielding
the uniform minimal base. Set `distroDefaults.enable = true` to refrain:
k3s then deploys its stock components through its own helm-controller, and
you configure them through HelmChartConfig — a day-2 concern, never
clan-rendered. servicelb/klipper
stays disabled in both modes: Cilium Node IPAM (D41) gives every classless
LoadBalancer Service node IPs.

## Options

Most cluster-wide settings live in `lib/kube-cluster` (`cluster-interface.nix`
and `node-interface.nix`): `cilium`, `pools`, `bootstrap.apply`,
`distroDefaults`, `coredns.rewrites`, and
the `packages.*` airgap escape hatches. The k3s service adds `configOverrides`,
extra keys merged into `/etc/rancher/k3s/config.yaml` (for example
`kubelet-arg`). A key the service renders, or a token, is an eval error: an
override would replace it silently, and a token would land in the Nix store.
There is no rke2 `profile = "cis"` equivalent. Servers run with
`secrets-encryption: true` (Secrets encrypted at rest in etcd).

## The first-server guard

`k3s-<instance>-init-guard` runs before `k3s.service` on the `clusterInit`
server whose etcd directory is missing. It dials the other servers' API
port after IfState and FRR: a connection means a cluster is alive, and
the server does not start; "connection refused" from every server means
no cluster; a timeout or no route is unknown, and after 300 s the guard
refuses. To start a new cluster anyway (the other servers are not up yet,
or the cluster is rebuilt from scratch), create
`/var/lib/rancher/k3s/server/allow-new-cluster-<instance>` and restart
`k3s.service`; the guard deletes the file when it lets k3s start.

## Airgap

The service imports the pinned k3s monolithic airgap archive plus the
artifact flake's digest-pinned Cilium image tarballs (matching the bundle's
manifest exactly). Override `packages.k3s` or `packages.images` to provide
a custom airgap set.

## Tests

Every suite runs on `routed-fabric` with Cilium native routing (D72
removed tunnel mode and `wireguard-mesh`). All are registered as
`clanTests` and exposed under `legacyPackages.x86_64-linux.vmTests`. Their
bodies are shared with RKE2 in `lib/kube-cluster/tests/vm/`; the files in
`tests/vm/` pass `distro = "k3s"`. Run them on the remote builder (see
[Testing](../../documentation/docs/reference/testing.md) for `--all`):

```bash
vm-test k3s-single --remote --quiet
vm-test k3s-join --remote --quiet
vm-test k3s-hostile --remote --quiet
vm-test k3s-ha --remote --quiet
vm-test k3s-data-plane --remote --quiet
```

- `k3s-single` — one server: initial PKI seed, haproxy LB, admin kubeconfig
  through the LB, certificate lifetimes and random serials, a changed bundle
  re-applied and pruned without a server restart, Cilium health, ClusterIP round-trip, CoreDNS (default +
  rewrite), a workload pod, and an etcd write/read smoke.
- `k3s-join` — one server + one agent. The agent joins through its LOCAL haproxy,
  both nodes become Ready with mesh InternalIPs, and Cilium is healthy on both.
- `k3s-hostile` — hostile actors: an outsider on the node LAN, a fabric
  leaf outside the cluster (`access = "client"`), a pod and a local user
  attack the cluster (scans, forced routes, BGP hijacks, the kubelet,
  etcd, the supervisor, secrets on disk). Every verdict prints
  `HOSTILE SAFE|GAP` with a positive control; any gap or failed control
  fails the suite (`K3S_HOSTILE_OK`).
- `k3s-ha` — three servers. All backends UP on every node's haproxy, three etcd
  voting members, then one manager is shut down: the survivors' healthchecks
  mark it DOWN, the API keeps answering through the local LB, fresh etcd writes
  succeed with 2/3 quorum, and pods still schedule.
- `k3s-data-plane` — the data-plane contract over the bootstrap bundle: the
  cluster comes up via the bootstrap-apply oneshot, a pool-backed Service
  (`io.cilium/bgp-control-plane` + selector) draws from the declared
  `CiliumLoadBalancerIPPool`, a classless Service gets node IPs from Node
  IPAM with the ETP-Local candidate restriction (backend pinned to one node),
  plus firewall positive/negative exposure. Hermetic: go-httpbin fixture,
  preloaded distro + Cilium airgap images.

## Modes

On a machine with network modes (the `modes` service), the per-machine
setting `modes = [ "developer" ]` limits this instance to those modes.
In the others the machine has none of its units, links, firewall rules
or sysctls; its secrets, exports and facts stay. Empty means every mode.
The service needs IfState, so a machine with a NetworkManager mode must
name the modes. An agent and a single-node cluster may be limited to some modes. A server of a cluster with other machines must stay in every mode: it is an etcd voter.
(`specs/netif.md` N4.)
