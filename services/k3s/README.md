# k3s

A thin [k3s](https://docs.k3s.io/) Kubernetes cluster service built on
`lib/kube-cluster`. It deploys an airgap-ready k3s control plane plus
Cilium (datapath mode derived from the `node_transport` — tunnel/VXLAN on
wireguard-mesh, native routing on routed-fabric; kube-proxy replacement,
Node IPAM) and CoreDNS — with the initial cluster PKI pre-generated by
clan vars and a per-node haproxy kube-apiserver load balancer.

For the cross-distro architecture, current-versus-planned capability matrix,
networking invariants, and delivery plan, see [SPEC.md](../../SPEC.md).

## Roles

- `server` — runs the control plane and, by default, workloads.
- `agent` — worker node.

## Quick start

```nix
{
  instances.kube = {
    module.name = "k3s";
    module.input = "self";
    roles.server = {
      settings.network.fabric = null;
      machines.alpha.settings = {
        clusterInit = true;
        network = {
          ipv4 = "10.0.0.1";
          ipv6 = "fd00::1";
        };
      };
    };
  };
}
```

`clusterInit = true` selects embedded etcd. Exactly one server per instance must
set it; joining servers and agents use `server` through their local haproxy.

## Node addressing

Set `settings.network.fabric` to a transport instance — a
`wireguard-mesh` (tunnel/VXLAN) or `routed-fabric` (native) instance —
to consume its `node_transport` export, or set `network.fabric = null`
and provide explicit
`network.ipv4`/`network.ipv6` per machine. D58 changes the exported
`node_transport` schema only, never this option. The service consumes only
the generic `node_transport` schemaVersion 2 and never branches on
provider service names (SPEC.md D58). The posture is all-or-none
(SPEC.md §6.3): mixing transport-provided and manual member addresses is
an eval error.

## Exports

The service consumes `node_transport` (schemaVersion 2, D58) and
publishes `kube_cluster` per member
machine (SPEC.md §6.2): schema version, cluster identity (name, resolved
cilium id, resolved dual-stack pod/service CIDRs, clusterDNS), mesh group,
transport
source, per-member mesh endpoints with effective topology labels, and pool
handoff facts. Fleet-wide assertions (duplicate names/ids, meshed-CIDR overlap,
node-in-two-clusters incl. cross-distro, mesh-group transport consistency) are
computed from these exports as `clan.checks` by the shared lib's fleet-checks
module.

## The per-node haproxy kube-apiserver LB

Every node — servers AND agents — runs a local haproxy bound to the node's own
transport addresses (both families):

- The kubeapi FQDN (`kubeapi-<instance>.<domain>`) resolves to the node's OWN
  address via `/etc/hosts`. Joining servers/agents, Cilium, and the admin
  kubeconfig all go through the local haproxy. Every member disables k3s's
  built-in agent client-side API LB so it keeps this path.
- k3s serves its HTTPS/kube-apiserver endpoint on `6443`
  (`https-listen-port`). The only LB frontend is the derived kubeapi port
  `7442 + <resolved cilium id>` (explicit pin or hashed default, SPEC.md
  §6.2); there is no separate RKE2-style supervisor frontend.
  Join URLs and the admin kubeconfig use the derived LB port, while haproxy
  backends target `6443`.
- Backends are every server member's transport addresses with TLS `/readyz`
  healthchecks. The check verifies the serving chain against the pre-generated
  server CA and presents a vars-issued client cert. A server lists itself plain
  and the remote servers `backup`; agents list all servers plain.
  `option allbackups` routes around dead backends.
- Stats page on `:8404` (password hash from the
  `rancher-haproxy-<instance>` var, rendered at eval).

## Vars bootstrap and CA lifecycle

`clan vars generate` pre-generates everything; nothing prompts:

- `rancher-pki-<instance>` (initializing server only) — the cluster CA tree and
  service-account key. A oneshot unit (`k3s-<instance>-pki-seed`) installs the CA
  material into `/var/lib/rancher/k3s/server/tls` before the first `k3s.service`
  start. It does not overwrite an initialized TLS tree and has no path watcher.
  Joining servers receive the cluster CA through k3s's normal bootstrap flow.
- `rancher-server-token-<instance>` / `rancher-agent-token-<instance>` — join
  tokens.
- `rancher-haproxy-<instance>` (every node) — the `/readyz` healthcheck client
  cert + CA chain + stats password hash.
- `rancher-admin-kubeconfig-<instance>` (servers only) — an operator client cert
  (CN=admin, O=system:masters) signed by the vars client CA; server URL is the
  kubeapi FQDN on the LB port. Linked to
  `/etc/rancher/k3s/admin-kubeconfig` on servers. k3s's native kubeconfig remains
  at `/etc/rancher/k3s/k3s.yaml`.

The datastore becomes authoritative after initialization. Rotate k3s CA
certificates with `k3s certificate rotate-ca`; do not regenerate vars to rotate
a live cluster's CA files.

## Cilium and CoreDNS

The service disables Flannel, k3s's network-policy controller, kube-proxy,
and (in the minimal base) the helm-controller. Cilium — plus the
`CiliumPodIPPool`, LB pools, and the clan CoreDNS serving `cluster.local`
(D46) — is
delivered by the kubenix bootstrap bundle, applied once via server-side
apply by a systemd oneshot on the `clusterInit` node (D40); nothing is
written to the k3s manifests dir. The bundle imports the artifact flake's
committed Cilium manifest and merges per-cluster variation (cluster
name/id, CIDRs, KPR endpoint, devices/MTU, Node IPAM) into the typed
resource tree — the chart is never re-run here (D26).

In the minimal base (`distroDefaults.enable = false`, the default, D42)
k3s's bundled CoreDNS is DISABLED (`--disable=coredns`) and the
clan-rendered CoreDNS serves `cluster.local` from the bundle; with
`distroDefaults.enable = true` the distro's stock CoreDNS deploys and the
bundle skips its own (D46, mode-exclusive). The clan Corefile imports the
`coredns-custom` ConfigMap per the k3s convention — but that ConfigMap is
OPTIONAL and GitOps-owned: clan NEVER renders it, and the deployment must
boot cleanly with it absent (D46). `coredns.rewrites` renders Corefile
rewrites into the clan CoreDNS, never the ConfigMap.
`coredns.helmValues` is rejected: k3s CoreDNS is not a Helm chart. No
member-facing private DNS service or VIP exists in either mode (D22,
day-2).

## distroDefaults

With `distroDefaults.enable = false` (the default, SPEC.md D42) the service
passes the k3s disable flags for the distro's packaged add-ons — Traefik,
local-storage, metrics-server — and disables the helm-controller, yielding
the uniform minimal base. Set `distroDefaults.enable = true` to refrain:
k3s then deploys its stock components through its own helm-controller, and
you configure them through HelmChartConfig — a day-2 concern, never
clan-rendered. servicelb/klipper
stays disabled in both modes: Cilium Node IPAM (D41) gives every classless
LoadBalancer Service node IPs.

## Options

Most cluster-wide settings live in `lib/kube-cluster` (`cluster-interface.nix`
and `node-interface.nix`): `cilium`, `pools`, `bootstrap.apply`,
`distroDefaults`, `coredns.rewrites`, and
the `packages.*` airgap escape hatches. The k3s service adds `configOverrides`,
extra keys merged into `/etc/rancher/k3s/config.yaml`. There is no rke2
`profile = "cis"` equivalent.

## Airgap

The service imports the pinned k3s monolithic airgap archive plus the
artifact flake's digest-pinned Cilium image tarballs (matching the bundle's
manifest exactly). Override `packages.k3s` or `packages.images` to provide
a custom airgap set.

## Tests

Single/join/HA suites run on `wireguard-mesh`; the data-plane and native
ClusterMesh suites run on `routed-fabric`. Additional tunnel, selective,
and external-LB suites cover both profiles. All are exposed as
`clan.nixosTests`:

```bash
nix build .#checks.x86_64-linux.k3s-single
nix build .#checks.x86_64-linux.k3s-join
nix build .#checks.x86_64-linux.k3s-ha
nix build .#checks.x86_64-linux.k3s-data-plane
```

- `k3s-single` — one server: initial PKI seed, haproxy LB, admin kubeconfig
  through the LB, Cilium health, ClusterIP round-trip, CoreDNS (default +
  rewrite), a workload pod, and an etcd write/read smoke.
- `k3s-join` — one server + one agent. The agent joins through its LOCAL haproxy,
  both nodes become Ready with mesh InternalIPs, and Cilium is healthy on both.
- `k3s-ha` — three servers. All backends UP on every node's haproxy, three etcd
  voting members, then one manager is shut down: the survivors' healthchecks
  mark it DOWN, the API keeps answering through the local LB, fresh etcd writes
  succeed with 2/3 quorum, and pods still schedule.
- `k3s-data-plane` — the data-plane contract over the bootstrap bundle: the
  cluster comes up via the bootstrap-apply oneshot, a pool-backed Service
  (`io.cilium/bgp-control-plane` + selector) draws from the declared
  `CiliumLoadBalancerIPPool`, a classless Service gets node IPs from Node
  IPAM with the ETP-Local candidate restriction (backend pinned to one node),
  plus firewall positive/negative exposure. Hermetic: go-httpbin fixture,
  preloaded distro + Cilium airgap images.
