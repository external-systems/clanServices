# rke2

A thin [RKE2](https://docs.rke2.io/) Kubernetes cluster service built on
`lib/kube-cluster`. It deploys an airgap-ready RKE2 control plane with
`cni: none` — Cilium (datapath mode derived from the `node_transport` —
tunnel/VXLAN on wireguard-mesh, native routing on routed-fabric;
kube-proxy replacement, Node IPAM),
pools, and a uniform clan-rendered CoreDNS for cluster.local (D46) come
from the kubenix bootstrap bundle, applied once via server-side apply by a
systemd oneshot on the `clusterInit` node (D40). The bundled `rke2-cilium`
and `rke2-coredns` charts are always disabled; nothing is written to RKE2's
watched manifests dir. The full cluster PKI is pre-generated by clan vars
and a per-node haproxy kube-apiserver load balancer fronts the API. With
`distroDefaults.enable = true` the distro's stock CoreDNS deploys instead
and the bundle skips its own (mode-exclusive); either mode renders ONLY
the in-cluster `cluster.local` CoreDNS — no member-facing private CoreDNS
service or VIP exists in either mode (SPEC.md D22, day-2).

For the cross-distro architecture, current-versus-planned capability matrix,
networking invariants, and delivery plan, see [SPEC.md](../../SPEC.md).

## Roles

- `server` — runs the control plane and, by default, workloads.
- `agent` — worker node.

## Quick start

```nix
{
  instances.kube = {
    module.name = "rke2";
    module.input = "self";
    roles.server = {
      settings.network.fabric = null;
      machines.alpha.settings = {
        clusterInit = true;
        network = {
          ipv4 = "10.0.0.1";
          ipv6 = "fd00::1";
        };
      };
    };
  };
}
```

## Node addressing

Set `settings.network.fabric` to a transport instance — a
`wireguard-mesh` (tunnel/VXLAN) or `routed-fabric` (native) instance —
to consume its `node_transport` export, or set `network.fabric = null`
and provide explicit
`network.ipv4`/`network.ipv6` per machine. D58 changes the exported
`node_transport` schema only, never this option. The service consumes only
the generic `node_transport` schemaVersion 2 and never branches on
provider service names (SPEC.md D58). The posture is all-or-none
(SPEC.md §6.3): mixing transport-provided and manual member addresses is
an eval error.

## Exports

The service consumes `node_transport` (schemaVersion 2, D58) and
publishes `kube_cluster` per member
machine (SPEC.md §6.2): schema version, cluster identity (name, resolved
cilium id, resolved dual-stack pod/service CIDRs, clusterDNS), mesh group,
transport
source, per-member mesh endpoints with effective topology labels, and pool
handoff facts. Fleet-wide assertions (duplicate names/ids, meshed-CIDR overlap,
node-in-two-clusters incl. cross-distro, mesh-group transport consistency) are
computed from these exports as `clan.checks` by the shared lib's fleet-checks
module.

## The per-node haproxy kube-apiserver LB

Every node — servers AND agents — runs a local haproxy bound to the node's own
transport addresses (both families):

- The kubeapi FQDN (`kubeapi-<instance>.<domain>`) resolves to the node's OWN
  address via `/etc/hosts`. Every Kubernetes client path that needs the API —
  joining servers/agents (`server` URL), Cilium (`k8sServiceHost`), the admin
  kubeconfig — goes through the local haproxy.
- The apiserver owns `:6443` and the supervisor `:9345` on every address, so
  the LB listens on the derived ports: kubeapi LB = `7442 + <resolved cilium
  id>` (explicit pin or hashed default, SPEC.md §6.2), supervisor LB =
  `+1000` (unique per cluster sharing one transport).
- Backends are every server member's transport addresses with TLS `/readyz`
  healthchecks (`check check-ssl` — the check connects with TLS, the data path
  stays raw end-to-end TCP). The check verifies the serving chain against the
  pre-generated server CA and presents a vars-issued client cert. A server
  lists itself plain and the remote servers `backup`; agents list all servers
  plain. `option allbackups` routes around dead backends.
- The supervisor backend's check probes the real API port (`check port 6443`)
  as the anti-deadlock signal: a joining server's supervisor is L4-up but
  cannot serve joins until its local apiserver is ready.
- Stats page on `:8404` (password hash from the `rancher-haproxy-<instance>`
  var, rendered at eval).

## Vars bootstrap (zero user input)

`clan vars generate` pre-generates everything; nothing prompts:

- `rancher-pki-<instance>` (servers only) — the cluster CA tree (root +
  intermediate + server/client/request-header/etcd-peer/etcd-server leaf CAs +
  the service-account key). A systemd unit (`rke2-<instance>-pki-sync-tls`,
  plus a path unit watching for regeneration) installs the CA material into
  `/var/lib/rancher/rke2/server/tls` before `rke2-server` starts — rke2 adopts
  the custom CAs instead of generating its own.
- `rancher-server-token-<instance>` / `rancher-agent-token-<instance>` — join
  tokens.
- `rancher-haproxy-<instance>` (every node) — the `/readyz` healthcheck client
  cert + CA chain + stats password hash.
- `rancher-admin-kubeconfig-<instance>` (servers only) — an operator client
  cert (CN=admin, O=system:masters) signed by the vars client CA; server URL
  is the kubeapi FQDN on the LB port. Linked to
  `/etc/rancher/rke2/admin-kubeconfig` on servers.

## distroDefaults

With `distroDefaults.enable = false` (the default, SPEC.md D42) the service
disables RKE2's packaged add-ons — ingress-nginx, metrics-server, snapshot
controller — and sets `ingress-controller: none`, yielding the uniform
minimal base. Set `distroDefaults.enable = true` to refrain: RKE2 then
deploys its stock components through its own helm-controller, configured via
HelmChartConfig — a day-2 concern, never clan-rendered. RKE2 ships no
servicelb/klipper; Cilium Node IPAM (D41) is the classless LoadBalancer
mechanism.

## Options

Most cluster-wide settings live in `lib/kube-cluster` (`cluster-interface.nix`
and `node-interface.nix`): `cilium`, `pools`, `bootstrap.apply`,
`distroDefaults`, `coredns.rewrites`, and
the `packages.*` airgap escape hatches. The rke2 service adds:

- `profile` — `"cis"` enables CIS hardening; other values are written to
  `config.yaml`.
- `configOverrides` — extra keys merged into `/etc/rancher/rke2/config.yaml`.

## Airgap

The service bundles the rke2 core image tarball from the pinned
`pkgs.rke2` package plus the artifact flake's digest-pinned Cilium image
tarballs (matching the bundle's manifest exactly). Override
`packages.images` / `packages.rke2` to provide a custom airgap set.

## Tests

Single/join/HA suites run on `wireguard-mesh`; the data-plane and native
ClusterMesh suites run on `routed-fabric`. Additional tunnel, selective,
and external-LB suites cover both profiles. All are exposed as
`clan.nixosTests`:

```bash
nix build .#checks.x86_64-linux.rke2-single
nix build .#checks.x86_64-linux.rke2-join
nix build .#checks.x86_64-linux.rke2-ha
nix build .#checks.x86_64-linux.rke2-data-plane
```

- `rke2-single` — one server: PKI sync, haproxy LB, admin kubeconfig through
  the LB, Cilium health, ClusterIP round-trip, clan CoreDNS (default
  cluster.local lookup + rewrite via direct pod-IP queries + a negative),
  a workload pod, and an etcd write/read smoke.
- `rke2-join` — one server + one agent. The agent joins through its LOCAL
  haproxy (kubeapi FQDN → own mesh address → LB supervisor port), both nodes
  Ready with mesh InternalIPs, Cilium healthy on both.
- `rke2-ha` — three servers. All backends UP on every node's haproxy, 3 etcd
  members, then one manager is shut down: the survivors' healthchecks mark it
  DOWN, the API keeps answering through the local LB, fresh etcd writes succeed
  with 2/3 quorum, and pods still schedule.
- `rke2-data-plane` — same data-plane suite as `k3s-data-plane` (bundle
  oneshot, pool allocation, Node IPAM classless Service with ETP-Local
  candidate restriction, firewall positive/negative), hermetic.
