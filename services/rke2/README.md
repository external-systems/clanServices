# rke2

A thin [RKE2](https://docs.rke2.io/) Kubernetes cluster service built on
`lib/kube-cluster`. It deploys an airgap-ready RKE2 control plane with
`cni: none` — Cilium (native routing over the `node_transport`, D72;
kube-proxy replacement, Node IPAM),
pools, and a uniform clan-rendered CoreDNS for cluster.local (D46) come
from the kubenix bootstrap bundle, applied at boot and on each deploy that changes it via server-side apply by a
systemd oneshot on the `clusterInit` node (D40). The bundled `rke2-cilium`
and `rke2-coredns` charts are always disabled; nothing is written to RKE2's
watched manifests dir. The full cluster PKI is pre-generated by clan vars
and a per-node haproxy kube-apiserver load balancer fronts the API. With
`distroDefaults.enable = true` the distro's stock CoreDNS deploys instead
and the bundle skips its own (mode-exclusive); either mode renders ONLY
the in-cluster `cluster.local` CoreDNS — no member-facing private CoreDNS
service or VIP exists in either mode (SPEC.md D22, day-2).

For the cross-distro architecture, current-versus-planned capability matrix,
networking invariants, and delivery plan, see [SPEC.md](../../SPEC.md).

## Roles

- `server` — runs the control plane and, by default, workloads.
- `agent` — worker node.

## Quick start

```nix
{
  instances = {
    # A one-machine fabric: routed-fabric is the only transport (D72),
    # and the cluster takes its node addresses from it.
    fabric = {
      module.name = "routed-fabric";
      module.input = "self";
      roles.spine.machines.alpha = {};
    };
    kube = {
      module.name = "rke2";
      module.input = "self";
      roles.server = {
        settings.network.fabric = {
          service = "routed-fabric";
          instance = "fabric";
        };
        machines.alpha.settings.clusterInit = true;
      };
    };
  };
}
```

A cluster always rides a fabric: its node addresses, links and MTU come
from the fabric's `node_transport` export (SPEC.md D72, D76). One machine
is a one-machine fabric, as above. `module.input = "self"` names the flake
that holds the services; use its input name in your clan. A nix-unit test
(`test_readmeQuickStart`) evaluates this inventory and expects no failed
assertion (H7).

`clusterInit = true` selects embedded etcd. Exactly one server per instance must
set it; joining servers and agents use `server` through their local haproxy.

## Node addressing

`settings.network.fabric` is required: the `routed-fabric` instance (or any
transport that implements the neutral `node_transport` schemaVersion 2,
D58) whose export gives every member its node addresses. The service never
branches on provider service names (SPEC.md D58). Every member must be in
that instance; a member without an export is an eval error. There are no
per-machine address options: manual addresses were removed in round 67
(D76).

## Who reaches what

The node firewall opens each port by source, from one matrix
(`lib/kube-cluster/firewall.nix`, SPEC.md §6.12). Every rule also needs a
fabric link or a local pod link; no link is trusted.

| Port | On | From |
|---|---|---|
| 6443 (API) | servers | members, the cluster's pods |
| 9345 (supervisor) | servers | members |
| 10250 (kubelet) | every node | servers; pods only with `firewall.kubeletFromPods = true` |
| 4240 (Cilium health) | every node | members |
| 2379, 2380 (etcd) | servers | servers |

The HAProxy fronts listen on loopback only, so no other host and no pod
reaches them. etcd's metrics port (2381) listens on loopback. A pod
reaches the API on a server and nothing else of a node. A metrics scraper
in a pod (metrics-server) needs `firewall.kubeletFromPods = true`.

## Exports

The service consumes `node_transport` (schemaVersion 2, D58) and
publishes `kube_cluster` per member
machine (SPEC.md §6.2): schema version, cluster identity (name, resolved
cilium id, resolved dual-stack pod/service CIDRs, clusterDNS), mesh group,
transport
source, per-member mesh endpoints with effective topology labels, and pool
handoff facts. Fleet-wide assertions (duplicate names/ids, meshed-CIDR overlap,
node-in-two-clusters incl. cross-distro, mesh-group transport consistency) are
computed from these exports as `clan.checks` by the shared lib's fleet-checks
module.

## The per-node haproxy kube-apiserver LB

Every node — servers AND agents — runs a local haproxy whose fronts listen
on loopback only (`127.0.0.1` and `::1`, D76):

- The kubeapi FQDN (`kubeapi-<instance>.<domain>`) resolves to loopback via
  `/etc/hosts`. Every Kubernetes client path that needs the API —
  joining servers/agents (`server` URL), Cilium (`k8sServiceHost`; its pods
  are host-network and read the node's `/etc/hosts`), the admin
  kubeconfig — goes through the local haproxy. No other host and no pod
  reaches a front.
- The apiserver owns `:6443` and the supervisor `:9345`, so the LB listens
  on the derived ports: kubeapi LB = `7442 + <resolved cilium id>`
  (explicit pin or hashed default, SPEC.md §6.2), supervisor LB on a
  server = `+1000`.
- An agent's supervisor front listens on `9345`, the supervisor's own port
  (an agent runs no supervisor). The agent's tunnel to the servers, which
  `kubectl logs` and `exec` ride, dials every server's node address on the
  port of the agent's join URL: with `9345` it reaches the real
  supervisor, which the firewall opens to members.
- Backends are every server member's node addresses with TLS `/readyz`
  healthchecks (`check check-ssl` — the check connects with TLS, the data path
  stays raw end-to-end TCP). Every server line pins its source to this
  node's address (`source`). The check verifies the serving chain against the
  pre-generated server CA and presents a vars-issued client cert. A server
  lists itself plain and the remote servers `backup`; agents list all servers
  plain. `option allbackups` routes around dead backends.
- The supervisor backend's check probes the real API port (`check port 6443`)
  as the anti-deadlock signal: a joining server's supervisor is L4-up but
  cannot serve joins until its local apiserver is ready.
- Loopback always exists, so haproxy starts before the fabric is up; a
  backend is DOWN until the fabric holds the node's address, then UP.
- The checks also verify that the certificate names the kubeapi FQDN
  (`verifyhost`).
- A read-only stats page on loopback (`127.0.0.1:8404`, `[::1]:8404`), with
  no password; the admin path is `/run/haproxy/haproxy.sock`.

## Vars bootstrap (zero user input)

`clan vars generate` pre-generates everything; nothing prompts:

- `rancher-pki-<instance>` (servers only) — the cluster CA tree (root +
  intermediate + server/client/request-header/etcd-peer/etcd-server leaf CAs +
  the service-account key). A systemd unit (`rke2-<instance>-pki-sync-tls`)
  installs the CA material into `/var/lib/rancher/rke2/server/tls` before a
  server's first start — rke2 adopts the custom CAs instead of generating its
  own. A later, different set (regenerated vars) is staged in
  `/var/lib/rancher/rke2/server/tls-staged` for `rke2 certificate rotate-ca`,
  never copied into the live directory: rke2 refuses to start on CAs newer
  than its datastore.
- `rancher-server-token-<instance>` (servers only) /
  `rancher-agent-token-<instance>` (every node) — join tokens. An agent joins
  with the agent token and never holds the server token.
- `rancher-clustermesh-ca-<group>` / `rancher-clustermesh-<instance>`
  (the `clusterInit` server only) — the ClusterMesh CA and leaf set; the
  secrets oneshot there is their one reader.
- `rancher-haproxy-<instance>` (every node) — the `/readyz` healthcheck client
  cert + CA chain.
- `rancher-admin-kubeconfig-<instance>` (servers only) — an operator client
  cert (CN=admin, O=system:masters, 365 days, random serial; renew with
  `clan vars generate --regenerate` on a branch) signed by the vars client CA; server URL
  is the kubeapi FQDN on the LB port. Linked to
  `/etc/rancher/rke2/admin-kubeconfig` on servers.

## distroDefaults

With `distroDefaults.enable = false` (the default, SPEC.md D42) the service
disables RKE2's packaged add-ons — ingress-nginx, metrics-server, snapshot
controller — and sets `ingress-controller: none`, yielding the uniform
minimal base. Set `distroDefaults.enable = true` to refrain: RKE2 then
deploys its stock components through its own helm-controller, configured via
HelmChartConfig — a day-2 concern, never clan-rendered. RKE2 ships no
servicelb/klipper; Cilium Node IPAM (D41) is the classless LoadBalancer
mechanism.

## Options

Most cluster-wide settings live in `lib/kube-cluster` (`cluster-interface.nix`
and `node-interface.nix`): `cilium`, `pools`, `bootstrap.apply`,
`distroDefaults`, `coredns.rewrites`, and
the `packages.*` airgap escape hatches. The rke2 service adds:

- `profile` — `"cis"` enables CIS hardening; other values are written to
  `config.yaml`. The default is `null`: CIS by default is planned (D25).
- `configOverrides` — extra keys merged into `/etc/rancher/rke2/config.yaml`
  (for example `kubelet-arg`). A key the service renders (and `profile`), or
  a token, is an eval error: an override would replace it silently, and a
  token would land in the Nix store.

## The first-server guard

`rke2-<instance>-init-guard` runs before `rke2-server.service` on the
`clusterInit` server whose etcd directory is missing. It dials the other
servers' API port after IfState and FRR: a connection means a cluster is
alive, and the server does not start; "connection refused" from every
server means no cluster; a timeout or no route is unknown, and after 300 s
the guard refuses. To start a new cluster anyway (the other servers are not
up yet, or the cluster is rebuilt from scratch), create
`/var/lib/rancher/rke2/server/allow-new-cluster-<instance>` and restart
`rke2-server.service`; the guard deletes the file when it lets rke2 start.

## Airgap

The service bundles the rke2 core image tarball from the pinned
`pkgs.rke2` package plus the artifact flake's digest-pinned Cilium image
tarballs (matching the bundle's manifest exactly). Override
`packages.images` / `packages.rke2` to provide a custom airgap set.
`packages.rke2` is also the runtime (`services.rke2.package`), so the
binary and its core images always come from one package.

## Tests

Every suite runs on `routed-fabric` with Cilium native routing (D72
removed tunnel mode and `wireguard-mesh`). All are registered as
`clanTests` and exposed under `legacyPackages.x86_64-linux.vmTests`. Their
bodies are shared with k3s in `lib/kube-cluster/tests/vm/`; the files in
`tests/vm/` pass `distro = "rke2"`. Run them on the remote builder (see
[Testing](../../documentation/docs/reference/testing.md) for `--all`):

```bash
vm-test rke2-single --remote --quiet
vm-test rke2-join --remote --quiet
vm-test rke2-hostile --remote --quiet
vm-test rke2-ha --remote --quiet
vm-test rke2-data-plane --remote --quiet
```

- `rke2-single` — one server: PKI sync, haproxy LB, admin kubeconfig through
  the LB, certificate lifetimes and random serials, a changed bundle
  re-applied and pruned without a server restart, a regenerated CA set staged
  while the server restarts on its live CAs, Cilium health, ClusterIP round-trip, clan CoreDNS (default
  cluster.local lookup + rewrite via direct pod-IP queries + a negative),
  a workload pod, and an etcd write/read smoke.
- `rke2-join` — one server + one agent. The agent joins through its LOCAL
  haproxy (kubeapi FQDN → own mesh address → LB supervisor port), both nodes
  Ready with mesh InternalIPs, Cilium healthy on both.
- `rke2-hostile` — hostile actors: an outsider on the node LAN, a fabric
  leaf outside the cluster (`access = "client"`), a pod and a local user
  attack the cluster (scans, forced routes, BGP hijacks, the kubelet,
  etcd, the supervisor, secrets on disk). Every verdict prints
  `HOSTILE SAFE|GAP` with a positive control; any gap or failed control
  fails the suite (`RKE2_HOSTILE_OK`).
- `rke2-ha` — three servers. All backends UP on every node's haproxy, 3 etcd
  members, then one manager is shut down: the survivors' healthchecks mark it
  DOWN, the API keeps answering through the local LB, fresh etcd writes succeed
  with 2/3 quorum, and pods still schedule.
- `rke2-data-plane` — same data-plane suite as `k3s-data-plane` (bundle
  oneshot, pool allocation, Node IPAM classless Service with ETP-Local
  candidate restriction, firewall positive/negative), hermetic.

## Modes

On a machine with network modes (the `modes` service), the per-machine
setting `modes = [ "developer" ]` limits this instance to those modes.
In the others the machine has none of its units, links, firewall rules
or sysctls; its secrets, exports and facts stay. Empty means every mode.
The service needs IfState, so a machine with a NetworkManager mode must
name the modes. An agent and a single-node cluster may be limited to some modes. A server of a cluster with other machines must stay in every mode: it is an etcd voter.
(`specs/netif.md` N4.)
