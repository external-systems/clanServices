Known correctness gaps that precede new features

A static code audit of the baseline found these issues. They do not invalidate the recorded boot/join/HA results; they show where those tests are blind.

  1. ETP Local is only documented, not rendered. Traefik Service values omit externalTrafficPolicy, leaving the normal default of Cluster. Arbitrary Helm values can also bypass the intended policy.
  2. RKE2's Traefik master switch does not disable every chart. Setting traefik.enabled = false changes the bundled ingress selection but does not suppress extra standalone RKE2 Traefik charts; k3s already gates its instance resolution. The zero-Traefik contract needs a positive RKE2 regression test.
  3. Cluster identity is not inventory-wide. Every instance defaults to id 1, no cross-distro duplicate/CIDR assertion exists, and ids 128–255 produce invalid derived IPv4 service addresses under the current formula.
  4. CIDR overrides are inconsistent. The shared pool renderer honors overrides while distro configuration still derives some values directly from the id. The new mandatory-dual-stack contract removes single-stack rendering rather than preserving these inconsistent branches.
  5. Custom certificates are duplicated and namespace-incomplete. They are rendered by the shared bootstrap and again by each distro; custom entries fail to suppress per-instance defaults, and a custom Certificate rendered in kube-system cannot satisfy a Gateway certificate reference in another namespace.
  6. Two airgap escape hatches are broken or unclear. The RKE2 package override selects artifact sources but is not wired to the running NixOS RKE2 package; the image override replaces rather than extends defaults without making that contract explicit.
  7. Some documented Traefik behavior is absent. The interface describes placement/anti-affinity behavior that the renderer does not produce, and disabling the ingress controller does not disable every provider. Documentation and rendering must be reconciled at the post-merge invariant boundary.
  8. Current tests miss important external behavior. The single-node suites use ClusterIP for Traefik, join/HA disable parts of the stack, and there are no runtime suites for LB policy, multi-Traefik, Sealed Secrets, ClusterMesh, BGP, PKI rotation, external CCM handoff, or the large add-ons.

2. Problem Statement

A clan operator should be able to declare machines and cluster instances in inventory.nix and receive working, secure, interconnected Kubernetes clusters—not a second, hand-operated networking project.

Today, an operator assembling k3s or RKE2 on bare metal must separately solve cluster bootstrap, CA and join-token handling, API failover, CNI replacement, pod/service addressing, ingress, certificates, LoadBalancer allocation, BGP, cross-cluster networking, add-on packaging, and firewall interactions. Most documentation assumes a cloud LoadBalancer, a flat L2 network, one cluster, one distro, or a live administrator running CLI commands. Those assumptions do not produce a declarative fleet.

The hardest requirements interact with one another:

  • Multi-cluster is an inventory problem. ClusterMesh needs unique names/ids, non-overlapping pod CIDRs, reachable node InternalIPs, compatible datapaths, shared trust, and remote API endpoints. Hand-editing each cluster cannot keep those facts coherent.
  • The transport must guarantee what the cluster promises. Pod, Service, and node networking are always dual-stack, even when a machine's physical underlay has only one family. The default cluster-owned WireGuard mesh supplies the missing family and encrypted L3 transport; native Cilium WireGuard and an explicitly configured unencrypted underlay must preserve the same dual-stack contract rather than silently losing a family.
  • Bare-metal LoadBalancing is an allocation, routing, and datapath problem. Cilium LB IPAM can allocate addresses, but something must deliver and, where appropriate, advertise them. A node's primary address, an address routed only to that node, and a shared BGP/ECMP VIP have different failure semantics and must not be conflated.
  • Node IPAM is not a universal answer. It reproduces k3s ServiceLB-like status for ordinary Services with real endpoints, but Cilium's own Ingress and Gateway Services use dummy endpoints and cannot use Node IPAM with ETP Local. A single ordinary LB-IPAM contract with explicit per-node address projection avoids that special case.
  • Ingress is not only HTTP. Real workloads need TCP, UDP, TLS termination, TLS passthrough, mTLS, and QUIC. One public IPv4 address cannot host every independent listener shape, so multiple Traefik instances and IPv6-first addressing must be normal.
  • Source preservation changes routing behavior. externalTrafficPolicy: Cluster can hide the client source for ordinary TCP/UDP Services and attract traffic to nodes without local endpoints. Clan-managed external proxy Services therefore require Local, with placement, advertisements, and tests that honor local endpoint presence. Cilium's special HTTP header behavior is not treated as a substitute for raw-L4 source preservation.
  • Address families are not symmetrical in the real world. The cluster is always dual-stack internally while a node may have only public IPv6, only public IPv4, both, or neither. Public exposure is per-node and per-Service; internal dual-stack never invents public reachability.
  • Artifacts and services have different release cycles. Every chart, image, CRD, and operator needs a pinned source and an atomic update path. Consumers should pin one coherent artifact repository revision rather than duplicate packaging or track artifact main.
  • Batteries included must not mean host-coupled day two. The base supplies CNI, CSI options, ingress/Gateway, LoadBalancer, BGP, cert-manager, and sealed-secret support, while tenants use Flux or Argo CD against those APIs without NixOS rebuilds.
  • Long-lived credentials do not replace rotation. RKE2/k3s leaf certificates already renew at service startup and their generated CAs have upstream-defined lifetimes. A proven staged rotation path is safer than an untested blanket 100-year certificate policy.
  • Misconfiguration needs an earlier failure boundary. Port collisions, overlapping CIDRs, duplicate ids, impossible TLS settings, inconsistent pool delivery, and conflicting firewall rules should fail at evaluation where possible; remaining behavior needs hermetic NixOS VM proof.

In short: the problem is not “install Rancher.” It is turning multi-cluster, multi-distro, software-defined networking and its operational safety rules into one coherent clan inventory contract.

3. Solution

Two thin public clanServices—rke2 and k3s—share one distro-neutral implementation, selectable dual-stack transport, and one Cilium-first networking contract. A separate artifact flake supplies pinned packages and sources; the inventory remains the only cluster topology declaration, while clan exports and vars distribute facts and credentials at build time.

Target architecture. This section and Section 5 describe the required end state, including unfinished work. Present-tense wording is normative shorthand for the target contract, not a claim that the capability exists at the imported baseline; Section 1 is always the current-status authority.

Target invariants

One declarative fleet

Adding an RKE2 or k3s instance is enough for it to receive a stable identity, non-overlapping defaults, integrated transport, and—when its mesh group has peers—automatic ClusterMesh configuration.

Dual-stack inside, always

Every cluster has dual-stack node InternalIPs, pod CIDRs, and Service CIDRs in every transport mode. Public exposure may independently be IPv4-only, IPv6-only, dual-stack, or absent per node and Service.

Cilium is the only CNI base

Every cluster uses one shared upstream Cilium 1.20+ profile, kube-proxy replacement, VXLAN tunnel mode, and multi-pool IPAM. Alternative CNIs and native-routing base modes are unsupported.

L3 only, with transport choices

No VLAN, L2 announcement, VRRP, or shared L2 requirement. Integrated host WireGuard is the default; native Cilium WireGuard and an unencrypted underlay are first-class alternatives with explicit dual-stack node facts. The cluster services absorb the mesh implementation rather than requiring a second inventory service.

Local external policy, always

Every externally exposed Service rendered for Traefik, ClusterMesh, or Cilium ingress/Gateway uses externalTrafficPolicy: Local. No Helm override may silently change it to Cluster; an upstream inability to honor the contract fails the feature gate.

One LB-IPAM model

Node-named Cilium LB pools own node transport, primary, and extra addresses. Clan-managed proxies use explicit per-node projections rather than Cilium Node IPAM, avoiding its dummy-endpoint limitation and making multi-IP status deterministic.

BGP only where routing needs it

Provider-, mesh-, assigned-, and statically routed node addresses are not re-advertised by default. Shared BGP VIPs use Cilium BGP v2 plus per-node BIRD for health-aware ECMP; route ownership is never ambiguous.

Cilium by default, Traefik first-class

One Cilium ingress and one Cilium Gateway supply the default HTTP/HTTPS and Gateway API path on declared node addresses, including the primary IPv4 on ports 80 and 443. Traefik remains a 0–N, fully tested alternative that can be the only ingress/Gateway implementation; additional instances default to IPv6-only alongside Cilium.

Topology is always labeled

Every node receives non-empty topology.kubernetes.io/region and topology.kubernetes.io/zone labels. Both default to the cluster instance name and can be overridden independently in per-machine settings.

cert-manager is base

cert-manager is always installed; there is no disable switch. Sealed Secrets remains optional and preserves a recoverable key history. Day-two issuers, routes, Services, and applications belong to Flux or Argo CD, not NixOS rebuilds.

Hermetic proof and operable PKI

All runtime dependencies are pinned in a dedicated artifact flake. Eval tests reject invalid inventories; NixOS VM tests exercise real traffic, BGP, certificate rotation, storage, and guest workloads offline.

4. User Stories

These stories define the intended consumer contract. “Operator” means the person writing the clan inventory; “maintainer” means someone changing the canonical services or artifact repository.

Cluster and fleet operators

  1. As a clan operator, I want to declare one server with one bootstrap flag, so that I get a working cluster without hand-writing Kubernetes configuration.
  2. As a clan operator, I want to choose RKE2 for one instance and k3s for another, so that I can use the right distro without learning two unrelated networking models.
  3. As a clan operator, I want the same role and add-on vocabulary across both distros, so that documentation and inventory patterns transfer cleanly.
  4. As a clan operator, I want to declare several cluster instances in one inventory, so that fleet topology is reviewable in one change.
  5. As a clan operator, I want integrated host WireGuard by default with native Cilium WireGuard and unencrypted-underlay alternatives, so that transport policy does not require a second mesh instance or a forked cluster service.
  6. As a clan operator, I want each cluster to receive a stable unique name and id, so that adding another cluster does not renumber existing clusters.
  7. As a clan operator, I want derived dual-stack pod and Service CIDRs that cannot overlap other clusters, so that cross-cluster traffic is unambiguous.
  8. As a clan operator, I want explicit id and CIDR overrides with collision checks, so that I can migrate existing addressing safely.
  9. As a clan operator, I want mixed RKE2 and k3s instances to discover one another through exports, so that I do not copy endpoints or credentials between them.
  10. As a clan operator, I want mesh groups, so that only mutually trusted clusters join the same ClusterMesh trust domain.
  11. As a clan operator, I want adding a second cluster to enable the mesh on both clusters after deployment, so that peering is declarative rather than a CLI follow-up.
  12. As a clan operator, I want removing a cluster from a mesh group to remove its remote configuration from survivors, so that stale peers do not linger.
  13. As a clan operator, I want a clear warning when an identity, CA, address-pool, or membership change is disruptive, so that I can plan the imperative reconciliation steps.
  14. As a cluster operator, I want cert-manager permanently present in the base, so that later add-ons and tenant Helm releases can rely on it.
  15. As a cluster operator, I want to disable the Rancher cloud controller and select an external CCM, so that AWS, hcloud, or another provider can be used without forking the service.
  16. As a cluster operator, I want day-two cluster changes to stay in Flux or Argo CD, so that application and tenant work does not rebuild the NixOS hosts.

Network and LoadBalancer operators

  1. As a network operator, I want an L3-only design with VXLAN tunneling, so that clusters work across routed bare-metal, VPN, and multi-cloud networks without VLANs.
  2. As a network operator, I want mandatory dual-stack node, pod, and Service addressing in every transport mode, so that cluster-internal contracts never depend on the physical underlay's families or encryption choice.
  3. As a network operator, I want an IPv4-only machine to receive mesh IPv6 in host-WireGuard mode, so that it can join the same dual-stack cluster as every other node.
  4. As a network operator, I want an IPv6-only machine to receive mesh IPv4 in host-WireGuard mode, so that dual-stack cluster APIs still work while public IPv4 exposure remains optional.
  5. As a network operator, I want per-machine node addresses, endpoints, ports, interfaces, MTU, routes, and pool blocks inside the cluster instance settings, including explicit overrides when host WireGuard is disabled.
  6. As a network operator, I want Cilium multi-pool IPAM with sensible non-overlapping defaults, so that pod allocation scales beyond the Kubernetes-default single pool.
  7. As a network operator, I want cluster CIDR overrides to drive every renderer consistently, so that Cilium, the distro, DNS, and assertions never disagree.
  8. As a network operator, I want every node's cluster-joining addresses added automatically to its node-named LB pool as exact /32 and /128 blocks, so that a single-node cluster needs no extra IP declaration.
  9. As a network operator, I want to add addresses and subnets to a node's pool through per-machine settings, so that additional capacity stays declarative.
  10. As a network operator, I want node InternalIP and ExternalIP facts to back the default Cilium ingress and Gateway LoadBalancers, so that simple clusters expose ports 80 and 443 without allocating a separate VIP.
  11. As a network operator, I want deterministic IPv6 carve-outs from a node's routed prefix, so that additional proxy instances can each receive one address per selected node.
  12. As a network operator, I want additional Traefik instances to default to IPv6-only addresses, so that Cilium can claim the node's first and only public IPv4 for the default web path.
  13. As a network operator, I want clan-managed proxies to receive an explicit list of per-node addresses, so that multi-node LoadBalancer status is deterministic rather than a single dynamic allocation.
  14. As a network operator, I want generic tenant Services to draw dynamically from labeled pools with documented one-per-family semantics, so that GitOps users can allocate LoadBalancers without Nix changes.
  15. As a network operator, I want per-node BIRD configured through Cilium's v2 BGP resources, so that I do not hand-maintain BGP speakers and peer files.
  16. As a network operator, I want exact IPv4 /32 and IPv6 /128 Service advertisements, so that upstream routers can install predictable host routes.
  17. As a network operator, I want ECMP toward endpoint-hosting nodes, so that north-south traffic uses available capacity without a separate load-balancer appliance.
  18. As a network operator, I want a BGP-routed VIP's next hop withdrawn from nodes without ready local endpoints, so that routers keep the VIP through healthy nodes instead of blackholing traffic.
  19. As a network operator, I want primary and statically delivered node addresses excluded from BGP advertisements by default, so that the control plane never competes with provider or WireGuard routing.
  20. As a network operator, I want eval-time port, pool, CIDR, ASN, delivery-mode, and interface checks plus targeted firewall rules, so that conflicts fail before packets are dropped mysteriously.
  21. As a network operator, I want standard region and zone topology labels to default to the cluster instance name with independent per-machine overrides, so that every node is labeled without forcing uniform physical topology.

Ingress, application, and security operators

  1. As an application operator, I want default Cilium ingress and Gateway instances with HTTP, HTTPS, and a default certificate, so that a minimal cluster has a useful CNCF-owned entry point.
  2. As an application operator, I want to disable all Traefik instances explicitly, so that Cilium-only, internal-only, or alternative-ingress clusters remain possible.
  3. As an application operator, I want multiple Traefik instances with distinct namespaces, Services, and IngressClasses, so that tenants and listener configurations do not collide.
  4. As an application operator, I want proxy placement and address projection to select the same nodes where web != false, so that no Service advertises a node without a local ready proxy.
  5. As an application operator, I want raw TCP and UDP entrypoints, so that non-HTTP protocols use the same declarative ingress model.
  6. As an application operator, I want TLS termination and SNI-based TLS passthrough, so that I can choose where certificates terminate per route.
  7. As an application operator, I want HTTP/3 over QUIC with the matching TCP and UDP Service paths and firewall openings, so that enabling it does not silently produce a TCP-only listener.
  8. As a network operator, I want externalTrafficPolicy Local on every clan-managed external proxy Service, so that raw client source addresses survive and routing reflects local endpoint health.
  9. As a security operator, I want mTLS through explicit TLSOption references and compatible IngressRoutes, so that client-certificate policy is not falsely promised on unsupported Gateway routes.
  10. As an application operator, I want Cilium as the default Gateway API implementation with the option to use only Traefik instead, so that the cluster matches my routing model without a manual controller installation.
  11. As an application operator, I want Cilium 1.20+ Gateway in ordinary LoadBalancer mode to support L4 and L7 without the old cilium-l4/cilium-l7 split, so that the interface reflects upstream capabilities.
  12. As an application operator, I want Cilium Ingress and Gateway to use ordinary LB IPAM rather than Node IPAM, so that the dummy-endpoint ETP Local limitation is avoided.
  13. As an application operator, I want at most one Traefik Gateway API controller per cluster with other instances isolated by IngressClass, so that route ownership is deterministic.
  14. As a security operator, I want cert-manager and an airgapped bootstrap CA installed unconditionally, so that TLS and dependent add-ons work before an external issuer is configured.
  15. As a security operator, I want to reference my own Issuer or ClusterIssuer for certificates, so that ACME, Vault, or other trust systems remain GitOps-owned rather than hardcoded here.
  16. As an application operator, I want CoreDNS rewrites, so that alias domains and tunnel-based access resolve to ordinary cluster Services.
  17. As an application operator, I want opt-in cross-cluster global Services, so that only explicitly shared workloads gain remote endpoints and discovery.
  18. As a security operator, I want a Sealed Secrets keypair generated and retained by clan vars by default, so that I can seal offline and recover decryption after a rebuild.
  19. As a security operator, I want native controller-generated Sealed Secrets keys as an explicit alternative with backup documentation, rather than a cert-manager Certificate that can overwrite the only private key.
  20. As a security operator, I want private keys and join tokens kept out of the Nix store, so that evaluation artifacts do not disclose cluster credentials.
  21. As a security operator, I want tested leaf and CA rotation runbooks for both distros, so that expiry and compromise response do not depend on rebuilding the cluster.
  22. As a security operator, I want expiry checks and staged rotation instead of blanket 100-year leaf certificates, with any long-lived offline root treated as an explicit custom-CA risk decision.

Add-on, platform, and edge operators

  1. As a platform operator, I want optional Multus with Cilium remaining the primary CNI, so that workloads can attach secondary networks deliberately.
  2. As a platform operator, I want OpenEBS LVM Local PV with thin-pool-aware StorageClasses, so that production local volumes can provision, expand, and snapshot.
  3. As a platform operator, I want OpenEBS ZFS Local PV on explicitly prepared nodes, so that mixed storage fleets do not require ZFS everywhere.
  4. As a platform operator, I want a central snapshot controller and per-engine snapshot classes, so that snapshot behavior is consistent and does not run duplicate controllers.
  5. As a platform operator, I want optional KubeVirt and CDI with per-node KVM preparation, so that I can import disks and run virtual machines beside containers.
  6. As a platform operator, I want kubelet CPU-manager and KubeVirt CPU-pinning options per node, so that mixed-core hosts can provide deterministic VM capacity.
  7. As an airgap operator, I want one pinned artifact-flake input to supply every chart, image, CRD, operator, and constructor, so that I do not duplicate packaging in each consumer.
  8. As an airgap operator, I want granular artifact packages rather than one mandatory mega-archive, so that disabled add-ons do not add gigabytes to a node closure.
  9. As a platform operator, I want both distros to use the same upstream Cilium and Multus versions, so that features and ClusterMesh compatibility do not depend on the distro's bundled mirror.
  10. As an airgap operator, I want an explicit non-airgap escape mode, so that connected environments can opt into pulls without changing the tested default.
  11. As a power user, I want merged distro and Helm overrides that cannot violate the core invariants, so that advanced configuration remains possible without silent unsupported shapes.
  12. As a platform operator, I want every clan-rendered manifest to carry consistent managed-by, instance, component, and content-hash labels, so that ownership is identifiable without changing selector labels.
  13. As a tenant operator, I want to use Flux or Argo CD against the base Gateway, Ingress, certificate, pool, and Service APIs, so that cluster day two does not churn the Nix repository.
  14. As an edge operator, I want 0–N optional HAProxy edge-proxy instances with one or more nodes each, so that one instance can consume exports from one or many downstream clusters without a one-to-one topology mapping.
  15. As an edge operator, I want TLS termination, HTTP caching, and PROXY protocol v2 by default toward Cilium or Traefik ingress endpoints, with passthrough and end-to-end TLS also available.
  16. As an edge operator, I want a vars-prompted directory containing one or more certificate pairs and a first-class Cloudflare mTLS toggle, so that edge certificates and client verification are declarative and recoverable.

  18. As an edge operator, I want explicit protocol boundaries—TCP, HTTP, HTTPS, TLS, mTLS, and optional VM-proven HTTP/3 termination, but no generic UDP relay—so that cache hits and HTTP/TLS offload do not depend on unsupported data paths.

  8. As the borg owner, I want to migrate only after the canonical implementation reaches the required parity and passes the affected suites, so that upstreaming does not regress the proven fleet and borg can drop its clan-community input.
  9. As a platform maintainer, I want upstream Kubernetes as a later first-class distro with the same Cilium and ClusterMesh contracts, so that distro choice is not limited to Rancher forever.
  10. As a platform maintainer, I want stable Cilium MCS-API support with CoreDNS integration and VM tests, initially disabled by default, so that cross-cluster discovery can mature without changing existing clusters implicitly.
  11. As a fleet maintainer, I want a later clan-operator with Inventory and Machine custom resources, so that clan lifecycle operations, health, topology visualization, and imperative reconciliation can run under Kubernetes without weakening the current declarative contract.

5. Implementation Decisions

The design is deliberately generic at the inventory boundary and opinionated in the rendered result. Users may choose distros, topology, addresses, and add-ons; they may not turn the result into a different, untested networking architecture through an override.

5.1 Module, artifact, and ownership boundaries

  • external-systems/clanServices is the canonical service repository. It owns the standalone flake, CI/release lifecycle, living specification, and day-to-day development. Consumers, including borg, use this repository without a clan-community input. Focused changes may still be proposed to clan-community for upstream review; upstream is a destination, not a consumer dependency.
  • Public rke2 and k3s services remain thin. They select distro runtime artifacts and own NixOS module options, bootstrap configuration, TLS-directory differences, chart-adoption differences, and join semantics. RKE2 retains its Supervisor path; k3s uses only its kube-apiserver endpoint.
  • The private Rancher cluster library owns parity. Shared interfaces, integrated transport, identity/CIDR resolution, Cilium, pools, BGP, Traefik, cert-manager, CoreDNS, Sealed Secrets, add-ons, vars generators, managed labels, and assertions live here.
  • The cluster services absorb the shared WireGuard implementation. No second inventory service is required. The standalone wireguard-mesh clanService may remain useful for ordinary NixOS machines, but Rancher and that service share one transport implementation rather than drifting into two WireGuard stacks. Every generated interface, key generator, firewall rule, and systemd unit is namespaced by cluster instance.
  • A dedicated public artifact flake is the single packaging input. external-systems/pkgs is the intended home. Borg is evidence and a future consumer, not the shared input other repos must absorb.
  • The artifact flake exports granular packages.<system> as its canonical API, an optional artifact-only overlays.default, pinned sources, and lib containing explicit-argument constructors plus version/lock metadata. It contains no inventory, clan vars, fleet labels, devshell policy, golden-image logic, or VM-test-specific runtime bundle.
  • RKE2 and k3s are built from source in the artifact repository. Release builds and upstream-HEAD development builds use the same constructors. “HEAD” means an explicitly resolved upstream commit whose revision and hash are locked by an atomic update—not an unfixed network fetch. Consumers still pin one immutable artifact-repository revision.
  • A normal locked flake input is the primary consumption path. The legacy lib/import-flake adapter inherited from clan-community remains optional for consumers that cannot declare the input directly; it is not a second required packaging interface. Temporary proving may use git+file:// or path: with an uncommitted lock override, but local URLs and home-directory paths are never committed.
  • Artifacts are granular and updated as atomic component sets: distro runtime + matching core artifacts, Cilium chart + images, Multus chart + images, cert-manager chart + images, each storage engine + snapshotter, and KubeVirt + CDI + tools. There is no mandatory all-add-ons archive. A consumer pins an immutable revision or tag, reviews the compatibility notes, updates explicitly, and runs its own static and VM gates; no consumer tracks artifact main.
  • The artifact repository proves source/hash/render/import consistency. The service repository proves NixOS and Kubernetes behavior. Final consumer proof uses a clean public fetch, not only a local path.
  • Node interface ownership is not blurred. Rancher consumes declared delivery facts and does not guess provider routing or silently reconfigure arbitrary public interfaces. Additional pool addresses must be marked as mesh/provider-delivered, assigned, statically routed to one node, or BGP-routed.
  • A future edge-proxy is a consumer, not a hidden dependency. Its HAProxy instances consume stable cluster/address exports and never become necessary for an in-cluster deployment.

5.2 Identity, topology, dual-stack CIDRs, and discovery exports

  • The Cilium cluster name defaults to the inventory instance name and must satisfy Cilium's 32-character lowercase DNS-style constraint.
  • cilium.id becomes nullable. The default is a stable hash of the instance name into 1–127, the safe derived-CIDR range; an explicit 1–255 override remains available. A hash collision is an eval error that requires an explicit id override—zero-configuration uniqueness is not guaranteed. Adding or removing other instances never changes an existing id.
  • Because IPv4 is always enabled internally, an explicit id above 127 always requires explicit IPv4 pod and Service CIDRs. No invalid 10.256… address may reach a distro. There is no single-stack branch and no placeholder family.
  • Before hashed defaults replace the current default id 1, existing inventories are migrated by pinning their current ids and CIDRs explicitly. The change must not silently renumber an established cluster; the migration and collision behavior receive eval tests.
  • One resolved, explicitly dual-stack CIDR structure feeds distro cluster-cidr, service-cidr, cluster DNS, Cilium values, pod pools, assertions, and exports. Both families are mandatory in every renderer.
  • Topology labels are always resolved. Cluster defaults set topology.kubernetes.io/region = instanceName and topology.kubernetes.io/zone = instanceName. Per-machine topology.region and topology.zone settings override either value independently; for example, one node can remain in region borg with zone texas, while another uses region foo and zone bar. Both rendered label values must be non-empty valid Kubernetes label values.
  • A neutral rancher_cluster instance-scope export publishes identity, mesh group, resolved pod/Service CIDRs, ClusterMesh endpoint addresses and port, pool handoff blocks, and schema version. Per-node node_transport exports carry mesh or explicit-underlay addresses, interface, MTU, primary/external address facts, delivery modes, and resolved topology. Secrets never appear in exports.
  • Both distro services select exports across service boundaries. Inventory-wide assertions reject duplicate names/ids, overlapping pod, Service, or linked-mesh CIDRs, duplicate NodePorts, missing cross-cluster transport peers, incompatible mesh settings, and missing topology labels before deployment.
  • Identity and CIDR changes are documented as disruptive on established clusters. The implementation must not “helpfully” renumber a cluster to resolve a collision.

5.3 Integrated transport and address-family contract

  • Host WireGuard is the default, not the only supported transport. The target interface exposes transport.mode = "host-wireguard" | "cilium-wireguard" | "unencrypted", defaulting to host-wireguard. The "unencrypted" value means the explicit unencrypted-underlay mode. API, supervisor, Cilium VXLAN, ClusterMesh, and ordinary east-west traffic use the selected routed L3 transport; no mode requires VLANs or shared L2.
  • Dual-stack cluster internals are unconditional in every mode. Node InternalIPs, pod CIDRs, Service CIDRs, Cilium address-family settings, and DNS rendering always include both families. An option to render a single-stack cluster is removed rather than repaired.
  • In host-WireGuard mode every node has both mesh IPv4 and mesh IPv6 addresses. Defaults derive deterministically from the stable cluster id and inventory machine name; per-machine settings can override addresses, listen port, endpoint, interface, MTU, extra routes, and pool blocks. A physical IPv4-only underlay therefore still supplies mesh IPv6, and a physical IPv6-only underlay still supplies mesh IPv4.
  • Native Cilium WireGuard is the first-class encrypted alternative. It disables the cluster-owned host WireGuard interface, keys, and units and enables Cilium's own transparent encryption. Every machine still supplies or derives valid dual-stack node InternalIPs, the transport interface, MTU, and required routes; the VM suite asserts both encryption and dual-stack behavior rather than accepting a config render alone.
  • The explicit unencrypted underlay is also first-class. It makes no confidentiality claim, disables host WireGuard and Cilium transparent encryption, and requires explicit per-machine dual-stack node addresses, interface, MTU, and any facts that the integrated mesh would otherwise generate. Missing families or transport facts are eval errors; no placeholder address or implicit single-stack fallback is allowed.
  • Per-cluster meshes do not imply isolated ClusterMesh islands. In host-WireGuard mode, members of one trust group render explicit cross-cluster peering from exported endpoints and public vars keys, with only remote mesh prefixes in AllowedIPs. The other modes must declare equivalent routed reachability. Every remote node InternalIP used by Cilium ClusterMesh must be reachable before peering is considered ready, and no secret key enters exports.
  • The supported datapath is routed L3 transport plus Cilium VXLAN. Host WireGuard cryptokey routing carries only declared mesh host prefixes and explicit extra routes; transport MTU minus VXLAN overhead determines Cilium's tunnel budget. Native-routing base mode remains outside the design.
  • Public family flexibility is distinct from cluster stack mode. A node may publish only public IPv6, only public IPv4, both, or neither. Each proxy instance selects its covered nodes and Service families independently: one family renders SingleStack; two render PreferDualStack by default, with RequireDualStack as an explicit strict option. No renderer invents an address or public route.
  • The distro HTTP-proxy setting is the documented escape for a node whose only external path is through a proxy. RKE2/k3s pass it to their own services, containerd, and kubelet; host environment and proxy variables are not automatically passed into pods. Application egress, NAT64/DNS64, and making an IPv6-only node reach an IPv4-only Internet endpoint are outside this service's networking guarantee.

5.4 Cilium and shared network artifact base

  • Both distros use the same canonical upstream Cilium chart and image profile, at version 1.20 or newer. RKE2's bundled Cilium is disabled; k3s does not adopt RKE2's Rancher-mirrored Cilium bundle. This makes BGP v2, Gateway API, and ClusterMesh behavior a deliberate shared version choice rather than a distro accident.
  • Multus follows the same rule: one upstream, atomically pinned chart/image profile for both distros unless a VM-proven distro incompatibility forces a documented adapter. RKE2 runtime/core/Traefik artifacts remain distro-specific.
  • Borg's removed upstream-Cilium lock machinery is prior art, not a file to resurrect blindly. Its later migration to RKE2-bundled artifacts avoided independent chart/image drift, and its per-architecture archives could not satisfy multi-arch index digest references. The artifact repository must preserve atomic versions and prove the chosen archive/digest model rather than reintroducing silent useDigest = false drift.
  • Always enabled: kube-proxy replacement, VXLAN tunnel mode, multi-pool IPAM, BPF masquerade/TProxy, Maglev, path-MTU discovery, and the default dual-stack pod pool.
  • Clan-managed proxy Services do not use Cilium Node IPAM. They use ordinary LB IPAM with explicit addresses. Node IPAM's ServiceLB-like behavior is therefore not needed for the default, and its dummy-endpoint incompatibility with Cilium Ingress/Gateway under ETP Local never becomes a special-case exception.
  • One Cilium ingress and one Cilium Gateway are the default public implementations. They use ordinary LoadBalancer Services and the same Local-only, explicit-address, and port-collision rules as Traefik. Cilium host-network mode is not used by the base: it disables the ordinary LoadBalancer path and rejects TCPRoute/UDPRoute. Traefik can replace Cilium as the only ingress/Gateway implementation or run additional instances beside it.
  • Post-merge validation rejects cilium.helmValues that change routing mode, tunnel protocol, IPAM mode, required dual-stack enablement, CNI chaining semantics, artifact profile, or Service policy invariants. Escape hatches customize the agreed architecture; they do not replace it unnoticed.
  • Enabling Multus changes the CNI chaining configuration explicitly and atomically. It is not emulated by unrelated raw Helm overrides.

5.5 Automatic, mixed-distro ClusterMesh

Actual peering is enabled automatically when more than one eligible RKE2/k3s instance belongs to the same mesh group. The default group includes all Rancher instances in the clan; an explicit group or opt-out separates trust domains. Every mesh-eligible cluster—including a singleton—runs the local clustermesh-apiserver and holds its certificates from first boot, but a singleton's remote-peer list is empty. Adding the first peer therefore updates configuration rather than introducing a new CA or a new local control plane; removing the last peer returns to that empty-list state without deleting certificates.

  • Peer lists are rendered from rancher_cluster exports into Cilium's declarative clustermesh.config.clusters structure. No cilium clustermesh connect or live kubeconfig exchange is part of deployment.
  • LoadBalancer is the default clustermesh-apiserver exposure. It uses the same ordinary LB-IPAM model as every other clan-managed proxy and exports stable addresses. A collision-checked NodePort mode remains an explicit escape for mesh-only deployments that deliberately do not want a LoadBalancer; it is not the default and must export the actual selected NodePort.
  • All server-role members are the endpoint and placement set by default. Each runs one clustermesh-apiserver replica with required anti-affinity/topology placement; the Service uses ETP Local and retains ClientIP session affinity for multi-replica deployments. Server membership changes update addresses, endpoints, placement, and certificate SANs together.
  • DNS fan-in gives every remote cluster one stable local name. Each remote cluster gets a selectorless local ClusterIP Service plus an eval-rendered EndpointSlice (or legacy Endpoints only where required for distro compatibility). Cilium's singular remote address points to that stable cluster-local DNS name, which fans out to all exported remote VIPs or node/NodePort endpoints. This preserves the useful part of the earlier implementation without its IPv4-only and weakly tested aspects.
  • The shared server certificate's SANs include every exported address and every DNS alias clients actually dial, including the local fan-in name and the clustermesh API DNS name derived from cluster name and mesh domain—not the Kubernetes API FQDN. The sorted endpoint set is a public validation input to the certificate generator, so membership changes reissue and roll certificates before new endpoints are advertised.
  • Dedicated ClusterMesh addresses are preferred. A primary address may be shared with Traefik or another Service only through an explicit lbipam.cilium.io/sharing-key projection with disjoint ports, the required cross-namespace annotations, and proof that every claimed address has the required local endpoints. For a BGP-routed VIP, all sharing Services must have identical ETP and local-endpoint coverage: BGP advertises an IP, not an IP/port pair, so one Service's healthy endpoint must not attract traffic that blackholes another Service on that node.
  • Every group member declares the identically named shared generator rancher-clustermesh-ca-<group> with share = true. Clan generates it once under vars/shared; no individual cluster owns it. Per-cluster dependent generators issue server/remote/local/admin certificates, which are synced as Secrets before Cilium starts. Authentication uses per-cluster identities and needs no cert-manager/CNI bootstrap dependency.
  • The CA and certificate contents never enter exports, Helm values, or the Nix store. Rotation is a separate two-phase CA-bundle design; regenerating a live mesh CA blindly is explicitly unsupported.
  • All peers use the same tunnel datapath and maxConnectedClusters value, have non-overlapping pod and linked-mesh CIDRs, and run the same pinned upstream Cilium profile. The trust group's selected cross-cluster transport must make every remote dual-stack node InternalIP reachable before Cilium peering starts; an API LoadBalancer alone is not treated as proof of ClusterMesh readiness. A future profile bump must remain within Cilium's documented compatibility window during rollout.
  • Cross-cluster global Services are opt-in per Service. Mesh membership alone does not export every workload. CoreDNS rewrites remain available for alias/tunnel naming. MCS-API is not part of the first ClusterMesh acceptance: implementation waits for upstream stability, ships with its CoreDNS wiring and VM tests, and remains disabled by default in its initial release. Any later default-on change is a separate reviewed migration.

5.6 Node LoadBalancing, LB IPAM, BGP, and BIRD

Every externally exposed clan-managed proxy is a Kubernetes LoadBalancer Service. Cilium-owned modes use ordinary Cilium LB IPAM, never Node IPAM; an explicit external class delegates allocation to another controller. The base distinguishes address delivery because allocation does not imply reachability or failover:

  • Every node receives one cluster-scoped, node-named CiliumLoadBalancerIPPool. Its initial blocks are the exact /32 and /128 cluster-joining mesh addresses. For example, a single node node-1 with join addresses 10.0.0.1/32 and fd0::1/128 gets pool node-1 containing exactly those blocks without further declaration.
  • Primary proxy addresses are explicit per-node facts. Declaring a public primary automatically adds its exact /32 or /128 block to that node's pool; it wins over the joining mesh address used as the fallback. Thus the zero-configuration example works on the mesh, while a normal bare-metal web node uses its public IPv4 and primary IPv6 on ports 80 and 443. Every projected address must belong to the corresponding node pool, and mesh reachability is never represented as public reachability.
  • The default Cilium ingress and Gateway Services project the complete computed address set with lbipam.cilium.io/ips. Pool serviceSelector labels authorize the request; the annotation supplies the selected node InternalIP/ExternalIP addresses, including the node's first and only primary public IPv4 for ports 80 and 443 where declared. This reproduces ServiceLB-like multi-node status without Node IPAM or a runtime guessing algorithm.
  • Additional Traefik instances default to deterministic IPv6-only projections when a node has a declared routed IPv6 prefix. A stable hash of cluster, node, and instance selects a carve-out and offset; an explicit offset overrides it and collisions are eval errors. Renaming or reordering unrelated instances must not renumber existing ones. Without a usable IPv6 carve-out, an additional external instance needs explicit addresses or a shared pool; it does not silently consume the last public IPv4.
  • Dynamic and projected allocation are different contracts. A generic tenant Service drawing by pool label receives one address per requested family for the whole Service, not one per node. Clan-managed multi-node proxies always use eval-time explicit projection. GitOps tenants may write their own explicit annotation if they deliberately want multiple addresses.
  • Per-node pools contain only addresses contributed by that node; shared public pools contain deliberately shared allocations. Pool names, labels, selectors, address ownership, delivery mode, and overlaps are checked at eval. Pool updates are potentially disruptive because Cilium may reassign addresses; they are reviewed as network changes, not harmless manifest tweaks.
  • Every node runs BIRD 2. Cilium's embedded GoBGP speaker uses the v2 CiliumBGPClusterConfig, CiliumBGPPeerConfig, CiliumBGPAdvertisement, and per-node CiliumBGPNodeConfigOverride resources; deprecated legacy BGP mode is never used.
  • The default local peering is Cilium dial-out to BIRD over loopback, with separate IPv4 and IPv6 sessions and eBGP multihop where required. Cilium does not open a competing TCP/179 listener.
  • The default ASN model assigns two deterministic private 32-bit ASNs per cluster—one to its BIRD instances and one to its Cilium speakers—plus a unique router id per node. Upstream AS paths therefore remain uniform. Advanced per-node ASNs are allowed only when the router supports AS-path multipath-relax.
  • BGP advertisement is opt-in per address class, not a consequence of pool membership. Only shared BGP VIPs and explicitly enabled CiliumPodIPPool prefixes are advertised. Primary, mesh, NIC-assigned, and statically delivered node addresses are not re-advertised by default, preventing competition with provider or WireGuard routes.
  • Advertisements select LoadBalancerIPs explicitly by label and family. Exact /32 and /128 routes are the default; aggregation is disabled under ETP Local and not offered as a shortcut around address planning.
  • BIRD import filters accept only expected exact Service VIPs and explicitly enabled CiliumPodIPPool prefixes. Upstream exports are limited to the same approved prefixes—never default, management, or transit routes. The advertised next hop is the node's reachable mesh transport address; broad kernel installation is not a default side effect.
  • With ETP Local and a BGP-routed VIP, Cilium advertises only on nodes with ready local endpoints. Tests prove that the failed node's next hop is withdrawn while the VIP remains through healthy nodes, and that direct node traffic avoids Service-level SNAT. No equivalent route-withdrawal claim is made for node-fate-bound addresses.
  • External routers peer with node BIRD over routed transport and must support enough ECMP paths, recursive next-hop resolution, and AS-path multipath-relax if node ASNs differ. Session loss is detected with explicit timers rather than assumed BFD; graceful restart is sized to real agent startup time. Routers never create duplicate WireGuard AllowedIPs.

5.7 Cilium, Traefik, and Gateway API

  • Cilium is the default ingress and Gateway API implementation. The target selector is ingressGateway.controller = "cilium" | "traefik", defaulting to cilium; despite living outside the gatewayAPI subtree, it governs both default ingress and Gateway API ownership. Selecting Traefik disables the default Cilium ingress/Gateway path so Traefik can be the only implementation; the old cilium-l4/cilium-l7 enum is rejected.
  • The clan-managed default Cilium Ingress and default Cilium Gateway are each 0–1 as a matter of base-policy scope, not an upstream controller limitation. They default on when Cilium is selected. Tenants may create additional Gateway resources through GitOps. Cilium 1.20+ in ordinary LoadBalancer mode supports HTTPRoute, TCPRoute, and UDPRoute on one Gateway without the old split.
  • The default Cilium web path uses declared node InternalIP and ExternalIP facts on ports 80 and 443. The same evaluated web != false node set controls placement, rendered node labels/affinity, pool projection, and firewall exposure. Where a node has only one public IPv4, Cilium's default path claims it; additional Traefik instances therefore default to deterministic per-node IPv6 projections rather than competing for that address.
  • Cilium Ingress/Gateway always uses ordinary LB IPAM with dedicated or explicitly shared addresses and ETP Local—never Node IPAM and never host-network mode. Full HTTP/HTTPS, L4/L7 Gateway, certificate, source-preservation, and BGP-pool acceptance tests must prove this upstream path on both distros; a dummy-endpoint or advertisement regression fails the feature instead of triggering a Cluster-policy fallback.
  • Traefik remains first-class with 0–N instances. No Traefik instance is required when Cilium is selected. An empty instance map means zero Traefik, and the master switch suppresses every bundled and standalone chart on both distros. Every instance is one release of the same pinned chart for that distro; extra instances use standalone chart resources and unique full names, namespaces, Services, and default IngressClasses.
  • At most one Traefik instance enables Traefik's Gateway provider because its controller name is shared upstream. When Cilium is the selected Gateway implementation, no Traefik instance claims that role; Traefik instances can still serve their own IngressClass-scoped ingress and CRD routes.
  • Every externally exposed Traefik or Cilium proxy Service renders ETP Local. Node-fate-bound address modes require full local coverage: DaemonSets are the Traefik default, while Deployments need required placement and at least one ready replica per covered node, with scale-to-zero and undersized HPA minima rejected. Routed BGP Deployments may scale to zero intentionally; BGP then withdraws every next hop.
  • Traefik EntryPoints cover HTTP, HTTPS, raw TCP, raw UDP, TLS termination, TLS passthrough, mTLS references, and HTTP/3. Container and exposed ports are separate; hostPort is always null. Raw UDP on Traefik uses IngressRouteUDP unless a pinned upstream version proves a Gateway UDPRoute path; Cilium 1.20+ UDPRoute is validated independently.
  • Port uniqueness is evaluated per covered node, address, and transport protocol. TCP and UDP may share a number; two conflicting listeners on the same family/address/protocol/port may not. LB IPAM, NodePort allocation, and Cilium do not perform the whole cross-instance check for us.
  • HTTP/3 adds the QUIC UDP listener, matching TCP and UDP Service ports, NetworkPolicy rule, and firewall opening together, normally through one mixed-protocol LoadBalancer Service. Separate TCP/UDP Services require explicit IP-sharing configuration. Maglev can stabilize backend selection but does not make an existing QUIC connection survive backend failure.
  • TLS passthrough leaves termination to the backend. mTLS enforcement uses IngressRoute-compatible TLSOptions; unsupported Gateway-route behavior is not claimed. Cilium's HTTP X-Forwarded-For behavior is documented separately from raw-L4 source preservation, and TLS-passthrough backends are not promised the original client address after Envoy creates a new upstream TCP connection.
  • The default certificate comes from cert-manager. Custom certificate entries render exactly once, in the namespace of their consumer, and suppress default per-instance certificates as documented. Tenant issuers, TLSStores, CA Secrets, and provider-specific integrations remain GitOps-owned.

5.9 Secrets, PKI, Sealed Secrets, and airgap

  • Clan vars own cluster CAs, join tokens, haproxy healthcheck material, admin kubeconfigs, the default Sealed Secrets key history, and ClusterMesh CA/certs. Public certificates may be read as public values; private material is referenced only by deployed secret paths.
  • RKE2 PKI sync remains non-destructive and distro-specific; k3s seeds only its initializing server and uses native CA replication/rotation thereafter. The shared library does not force RKE2 semantics onto k3s.
  • cert-manager does not generate the Sealed Secrets sealing key in the base design. A Certificate can create a Secret mechanically, but cert-manager reissuance and private-key rotation do not implement Sealed Secrets' append-new/preserve-old key registry, controller reload, public-cert distribution, or backup semantics. Preventing old ciphertext from becoming undecryptable is more important than reusing the convenient controller.
  • Vars-managed Sealed Secrets keeps native renewal disabled and retains every old key. Controller-managed mode uses native generation and retention with an explicit backup/restore runbook. Any future cert-manager integration is a separate orchestration feature requiring key history, rotationPolicy analysis, controller restart, newest-cert publication, and recovery tests—not a one-resource option.
  • Airgap-ready is the tested default. Every new feature lands with its artifact-flake source pin, complete image set, digest/NAR locks, and build-time manifest-to-lock consistency check in the same change. Consumers update the artifact input and their own compatibility checks together.
  • A single explicit airgap disable switch may permit registry access in connected environments. It never changes pinning or tests, and all VM suites keep airgap enabled.
  • Override contracts are explicit: artifact replacement requires a complete replacement set; additive image lists extend defaults. The RKE2 package override must control both the runtime and the matching artifact extraction source.

5.10 Live certificate rotation and imperative lifecycle

  • The base ships a tested per-distro rotation runbook and a guarded helper, not a promise that Nix activation rotates live PKI safely. The helper checks expiry and cluster health, backs up required state, stages files outside the active TLS directory, preserves keys where required, executes the distro-native command, and verifies nodes, API access, and workloads afterward.
  • Leaf rotation follows upstream behavior: RKE2/k3s client and server certificates are valid for 365 days and renew at service startup when expired or within the upstream renewal window. Manual key+cert rotation uses rke2 certificate rotate or k3s certificate rotate with the service stopped, then restarts and verifies it. Automated leaf renewal is retained.
  • CA rotation uses a separate staging directory and rke2 certificate rotate-ca --path=/opt/rke2/server or k3s certificate rotate-ca --path=/opt/k3s/server. It never overwrites the active TLS directory. Same-root custom-CA renewal can be non-disruptive; a new root is explicitly disruptive, may require --force, new secure-token configuration, admin kubeconfig replacement, server/agent restarts, and pod restarts. The runbook includes those steps rather than hiding them behind a successful command exit.
  • The service-account signing key receives its own rotation path. Existing keys are appended/retained where upstream requires them so old service-account tokens are not invalidated. CA rotation and Sealed Secrets rotation are different operations and never rotate application Secret values implicitly.
  • A blanket 100-year cluster certificate default is rejected. Upstream generated CAs are normally 10-year and leaf certificates 365-day; there is no ordinary supported config switch that makes the whole PKI 100-year. An installation may deliberately provide a long-lived offline custom root, even 100-year, but that is an explicit risk decision with intermediates, leaves, backups, and rotation still governed by this runbook.
  • Rotation acceptance runs on live single-node and HA VMs: check expiry, rotate leaves, rotate CA with the same root, exercise the documented new-root branch in a disposable fixture, preserve service-account tokens where promised, and prove API/workload/Sealed Secrets behavior afterward.
  • Inventory deletion is not cluster garbage collection. Removing a machine does not drain it, delete its Kubernetes Node object, or remove its etcd member; removing a cluster does not erase remote peers, external addresses, data, or backups. The operator runbooks cover cordon/drain, Node deletion, distro-native etcd membership removal with quorum checks, mesh-peer cleanup, and safe name/address reuse.
  • Changing pool blocks, CIDRs, cluster ids, shared CA roots, or ClusterMesh membership is a reviewed operational change with documented reconciliation. Declarative rendering remains the source of the desired end state, while these unavoidable imperative steps are explicit and tested where feasible.

5.11 External CCM, managed manifests, and GitOps ownership

  • Cloud-controller selection is generic: cloudController = "none" | "rancher" | "external". none disables the distro/Rancher CCM for the built-in bare-metal path; rancher preserves the distro-managed controller; external disables the built-in controllers, selects external kubelet/cloud-provider mode, and accepts operator-supplied CCM configuration.
  • AWS, hcloud, and other CCM implementations, credentials, provider flags, and provider-specific LoadBalancer classes are not bundled into the shared base. An external CCM may be rendered through the generic chart/manifest escape or installed by GitOps. The service only guarantees the correct distro handoff and does not prevent the external controller from owning its documented Service classes.
  • A hermetic fake external CCM validates the handoff in VM tests: nodes receive the expected provider/address behavior, the Rancher CCM stays disabled, and Cilium-owned Services remain distinct from external-class Services. Real AWS/hcloud acceptance is provider-specific operational validation, not a requirement for the offline suite.
  • Every manifest rendered by these services carries non-selector ownership labels: app.kubernetes.io/managed-by: clan, rancher.clan.lol/managed: "true", rancher.clan.lol/instance, rancher.clan.lol/component, and a short rancher.clan.lol/config-hash. Larger provenance belongs in annotations. Hashes and ownership labels never enter immutable selectors, and secrets never enter either field.
  • The clan-rendered layer is the opinionated base, not the cluster's day-two control plane. It installs APIs and a small set of base resources, then leaves tenant issuers, TLSOptions/TLSStores, Routes, Services, pool claims, and applications to Flux or Argo CD. Neither GitOps controller is required by the base.
  • Clan does not continuously reclaim tenant resources or require a NixOS rebuild for their changes. Base upgrades must preserve tenant CRDs and documented extension points; a tenant can create a Gateway, IngressRoute, Certificate, or generic LoadBalancer Service and use it without host activation.

5.12 Assertions and firewall behavior

  • Evaluation rejects impossible topology: multiple bootstrap servers, duplicate ids/CIDRs/ports, missing dual-stack transport or CIDR families, missing region/zone labels, multiple Gateway controllers, invalid entrypoint/TLS combinations, duplicate certificates, and uncovered certificate references.
  • Pool assertions reject overlaps, unknown delivery modes, per-node address ownership mismatches, unstable hash collisions, dynamic multi-node assumptions, unavailable requested families, unsafe shared-VIP topology, and BGP advertisement of provider/mesh-owned primary addresses.
  • Placement assertions compare the complete projected address set with the nodes that can host ready local endpoints. ETP Cluster, missing local coverage, Cilium Node IPAM on clan-managed proxies, Cilium host-network mode, and a disabled cert-manager are invalid post-merge states.
  • Transport assertions reject missing node addresses, interfaces, or MTU in native-Cilium-WireGuard and unencrypted modes, and reject host-WireGuard resources rendered outside their own mode. Encryption never substitutes for the mandatory second address family.
  • Assertions inspect the fully merged values where an escape hatch could violate an invariant. Testing only defaults is insufficient. Artifact assertions also require the selected runtime and chart/image profile to be coherent and completely locked.
  • Firewall rendering follows interface trust boundaries: API and haproxy stay on declared cluster transport; public listener ports open only where the corresponding Service actually exposes them; ClusterMesh and BGP ports are restricted to expected peers; HTTP/3 opens UDP as well as TCP.
  • VM tests assert both positive connectivity and negative exposure. A missing debug binary or empty capture is a test failure, not evidence that a packet path works.

5.13 Reserved optional HAProxy edge design

The future edge-proxy runs HAProxy on ordinary NixOS machines. It is entirely optional, is not a Kubernetes member, and exists to offload HTTP and TLS work from cluster nodes. It supports 0–N instances with one or more nodes per instance; each instance consumes one or many clusters' exported Cilium or Traefik ingress/Gateway endpoints. It is implemented only after those cluster contracts stabilize.

  • The primary mode is TLS termination at HAProxy, forwarding to an in-cluster Cilium or Traefik Service endpoint. TLS may instead pass through or terminate and re-encrypt for end-to-end TLS. The default downstream is the selected cluster's exported default ingress/Gateway endpoint set, but an instance may address additional exported proxy instances explicitly.
  • Certificate material comes from clan vars. Prompts accept one or more certificate/private-key pairs and render them into a HAProxy certificate directory. Private keys remain encrypted at rest in the repo and are referenced only by deployed secret paths; certificate naming, SAN coverage, and stale-file behavior are part of the interface and tests.
  • Cloudflare client-certificate verification is a first-class toggle. The Cloudflare mTLS profile configures the appropriate client CA and verification behavior explicitly; it does not silently trust every client CA or claim end-to-end client identity after termination. End-to-end client authentication uses TLS passthrough instead.
  • The terminate-and-cache profile offloads eligible HTTP responses. Cache keys, eligibility, TTLs, invalidation/purge, tenant isolation, and origin-consistency tests are explicit. Private or otherwise ineligible responses are not cached merely because the profile is enabled.
  • PROXY protocol v2 is on by default between compatible hops. The downstream Cilium or Traefik listener must explicitly enable and trust it for the edge's addresses. ETP Local remains required in-cluster; PROXY protocol is not an excuse for Cluster, and forwarded client identity is accepted only from explicitly trusted proxy hops.
  • Protocol support is stated precisely. HAProxy provides TCP and HTTP/HTTPS proxying, TLS termination, SNI-based TLS passthrough, client-certificate mTLS, HTTP caching, and health-checked backend load balancing. A QUIC-capable pinned HAProxy build may offer HTTP/3 termination as a separately proven profile with HTTP/1.1 or HTTP/2 downstream. HAProxy does not provide a generic UDP relay; raw UDP/QUIC forwarding is outside this service.
  • One edge deployment may consume many cluster exports and route to many downstream Cilium or Traefik instances. Separate edge instances are for administrative, listener, certificate, or addressing isolation—not an artificial one-to-one mapping requirement.
  • HAProxy backend balancing is not BGP or IP failover. HAProxy can select healthy downstream endpoints, but it does not speak BGP, advertise pools, or provide ECMP itself. BIRD or another routing service may compose with exported endpoint/pool facts to advertise edge VIPs or downstream blocks. IP failover, route withdrawal, and address ownership remain the user's NixOS modules or another custom clanService.
  • The first edge acceptance suite covers multiple downstream clusters, vars-provided certificate pairs, TLS termination and passthrough, Cloudflare mTLS accept/reject behavior, the explicit cache profile, default PROXY protocol v2, and downstream/edge failure behavior. HTTP/3 termination is a separate opt-in suite only when the pinned HAProxy build supports it. Generic UDP relay and edge-owned IP failover are not acceptance requirements.

5.14 Decisions explicitly superseded

  • The canonical implementation now lives in external-systems/clanServices. Clan-community remains an upstream review destination, not a required flake input for borg or other consumers.
  • Single-stack clusters are removed. The target is always dual-stack internally; only public Service families vary. This supersedes the earlier plan to repair and test IPv4-only and IPv6-only cluster rendering.
  • Rancher no longer requires a separately instantiated mesh, and host WireGuard is no longer mandatory. Each cluster absorbs the shared implementation and defaults to host WireGuard, with native Cilium WireGuard and unencrypted-underlay alternatives that preserve dual-stack behavior.
  • Cilium Node IPAM is not the default LoadBalancer mechanism. Ordinary LB IPAM plus explicit per-node projection supplies ServiceLB-like addresses without the Cilium Ingress/Gateway dummy-endpoint exception.
  • ETP Cluster is rejected for clan-managed externally exposed proxy Services. This supersedes older notes that required Cluster for Node IPAM or allowed it for Traefik Deployments. No silent fallback is permitted when an upstream path cannot honor Local.
  • ClusterMesh is not a manual post-install step, and NodePort is not its default. Declarative exports and certs remain; LoadBalancer is canonical, NodePort is an explicit escape, and the old selectorless-Service endpoint fan-in is retained.
  • Cilium, not Traefik, is the default ingress and Gateway API implementation. The cilium-l4/cilium-l7 split remains removed: Cilium 1.20+ ordinary LoadBalancer Gateway mode supports L4 and L7. Traefik is a fully supported 0–N alternative and can be the only implementation.
  • The reserved external edge is HAProxy edge-proxy, not a Traefik binary service. Its first-class job is HTTP/TLS termination and caching toward downstream Cilium or Traefik; BGP, ECMP advertisement, and IP failover are not built into it.
  • cert-manager is no longer optional. It is base. Conversely, Sealed Secrets key generation is not delegated to a plain cert-manager Certificate merely because cert-manager is present.
  • A blanket 100-year cluster certificate policy is not accepted as a rotation shortcut. Upstream leaf renewal and a proven staged CA rotation runbook are the base; long-lived custom roots are explicit exceptions.
  • Borg and RKE2-bundled Cilium are not shared packaging APIs. A dedicated artifact flake serves consumers, and both distros use one upstream Cilium/Multus profile. Borg's implementation remains evidence, not something to copy blindly.

5.15 Reserved platform evolution

  • Upstream Kubernetes is a later first-class distro. It must consume the same identity, transport, Cilium, artifact, export, and ClusterMesh contracts and prove mixed-cluster behavior before it joins the supported distro matrix. It is not part of the current RKE2/k3s implementation.
  • Cilium MCS-API waits for upstream stability. The eventual implementation includes its special CoreDNS configuration and full ClusterMesh VM coverage, but ships disabled by default. Existing opt-in global Services remain the initial discovery contract; any later default-on migration is reviewed separately.
  • A future clan-operator is a separate lifecycle platform. Inventory and Machine custom resources will wrap the clan HTTP server and CLI for CRUD operations, manage inventory.nix, and orchestrate imperative work such as PKI rotation, machine creation/deletion, service membership changes, updates, and health checks. A user-facing topology UI is also reserved. The operator does not replace the current declarative flake contract and is not a dependency of these services.

6.2 Test quality rules

  • Tests are hermetic and offline. A registry, chart repository, or internet request during a test is a defect in the pin, not something to mock away. Final artifact-consumer proof also starts from a clean checkout and immutable public revision.
  • Assertions use eval-time-deterministic addresses and ports. Runtime-allocated values are read and checked against their allowed semantics, never hardcoded from a previous run.
  • Every boot/join test asserts dual-stack node, pod, and Service addressing in the selected transport mode even when the physical test underlay exposes only one family. Public-family tests are separate from cluster-stack tests.
  • VM tests check round-trips and failure behavior, not only that a pod exists. Examples: an HTTPS response validates the CA, a UDP echo returns the payload, an HTTP/3 client uses QUIC, a BGP-routed VIP loses only the failed node's next hop, and a restored snapshot contains the original file.
  • Negative assertions matter: no single-stack cluster rendering, no public API listener, no ETP Cluster in clan-rendered external proxy Services, no Node IPAM on those Services, no foreign-IngressClass route, no image pull, no primary-address BGP advertisement, no next hop from a node without a ready local endpoint, and no host-WireGuard resources in the non-host modes.
  • Operational tests verify the postcondition, not just the command: after PKI rotation the API and workloads still function; after Sealed Secrets recovery old ciphertext still decrypts; after node removal the etcd member and Node object are explicitly reconciled by the runbook.
  • Tests fail fast on crash loops and missing diagnostic tools. No timeout inflation, skipped assertion, weakened protocol check, or fallback to Cluster policy is an acceptable fix.
  • Sandboxed runs are authoritative. Driver mode is for diagnosis only. VM suites run one at a time to avoid KVM, RAM, disk, and timing collisions.

  • Automatic ClusterMesh across different clan inventories, unrelated administrative domains, or mutually untrusted clusters. Exports and trust are intentionally inventory-scoped.
  • Automatic global exposure of every Service merely because clusters are meshed. Global Services remain explicit.
  • MCS-API before upstream stability, or an initial MCS-API implementation enabled by default. Cilium Global Services and pod-to-pod behavior come first; later MCS support ships disabled until a separate migration decision.
  • Bundled AWS/hcloud/other provider CCM implementations, credentials, provider-specific CSI, or provider hacks in the shared base. The generic external-CCM handoff is supported; the provider implementation remains operator-owned.
  • Longhorn, Mayastor, iSCSI, or replicated-storage promises. OpenEBS Local PV is node-local.
  • Cluster-side provider-specific certificate issuers, Cloudflare account resources, tenant TLSStores, application routes, or the day-two application lifecycle inside NixOS. Those remain GitOps-owned behind generic interfaces. The optional edge's operator-supplied Cloudflare client-CA profile is not a Cloudflare account integration.

  • Direct-to-pod routing from the HAProxy edge. The edge targets exported ingress/Gateway Service endpoints; it does not assume that external hosts can reach VXLAN pod addresses.
  • Public Internet family remediation, NAT64/DNS64, or automatic pod proxy configuration. The distro HTTP-proxy setting covers only its documented RKE2/k3s/containerd/kubelet path; application egress remains workload-owned.
  • Generic UDP or raw QUIC relay through HAProxy, HAProxy-native BGP, or edge-owned IP failover. Optional HTTP/3 termination requires a capable pinned build and its own VM proof; backend balancing must not be presented as route advertisement.
  • Untested HTTP caching or HTTP/3 behavior. The terminate-and-cache profile requires explicit eligibility and invalidation rules, and every optional protocol profile requires behavioral tests.
  • Blanket 100-year leaf certificates, a cert-manager-generated Sealed Secrets key without key-history orchestration, or automatic blind regeneration of live CA roots.
  • Fully declarative node/etcd/cluster deletion, non-disruptive cluster-id changes, or in-place conversion between RKE2 and k3s. The required imperative runbooks are part of the deliverable.
  • A production external edge implementation before the multi-cluster endpoint, certificate, and downstream ingress contracts it consumes are VM-proven.

9.2 Important upstream constraints

  • ClusterMesh joins one trust domain. Cilium explicitly recommends connecting only mutually trusted clusters with equivalent security postures.
  • Cilium Node IPAM selects candidates from EndpointSlices under ETP Local and explicitly rejects its own dummy-endpoint Ingress/Gateway Services in that mode. Ordinary LB IPAM avoids that allocation path, but the resulting Cilium behavior still requires VM proof.
  • Cilium LB IPAM allocates addresses; another mechanism must deliver and, where required, advertise them. A dynamic draw is not a per-node projection, pool updates can reassign addresses, and overlapping pools conflict.
  • Cilium BGP advertises routes but does not replace the Service datapath. With ETP Local, LoadBalancer advertisements track local ready endpoints. Advertisements are per IP, not per IP/port pair, which constrains safe VIP sharing.
  • Cilium 1.20+ ordinary LoadBalancer Gateway mode supports L4 and L7 routes; host-network mode is different and rejects TCPRoute/UDPRoute. The specification deliberately uses the former.
  • Cilium's per-node Envoy preserves HTTP source information in both ETP modes through forwarding headers, but TLS passthrough and raw UDP/TCP have different backend source semantics. No blanket client-IP claim is inferred from HTTP behavior.
  • Traefik's Kubernetes providers can run outside a cluster, but direct endpoint routing still requires network reachability and appropriately scoped API credentials. UDP routers have no Host/SNI matching.
  • Traefik OSS routing and TLS termination do not by themselves define an HTTP cache. The narrow terminate-and-cache profile uses a cache-capable implementation with explicit eligibility and invalidation behavior.
  • RKE2 and k3s leaf certificates renew at service startup; generated CAs are not automatically renewed. CA rotation is staged through distro-native commands, and root replacement can invalidate tokens and trust.
  • Sealed Secrets renewal adds a new key while retaining old active private keys. It does not re-encrypt existing SealedSecrets or rotate the application Secret values, and cert-manager does not supply that lifecycle automatically.
  • Distro HTTP-proxy settings do not automatically propagate host environment or proxy configuration into pods.
