# Data-plane hardening plan

Status: **phase 3 in progress**; phases 1–2 are complete. D64 locks the
clan-vars allocation contract before its implementation commits. SPEC.md
stays the status authority, and each phase below amends SPEC.md before it
changes code (AGENTS.md rule 3).

Goal: make the Data-plane contract (SPEC.md §3.2) enforceable and stable on
any underlay — bare metal, Proxmox, Hetzner, GCP, later AWS and Azure — by
testing it under real-world conditions instead of one flat L2 segment.

### Cross-cutting

1. **IPv6 RA on forwarding nodes.** netif sets per-link `accept_ra = 1`;
   k3s/rke2 and spines/borders enable IPv6 forwarding. Linux ignores RAs at
   `accept_ra = 1` when forwarding is on (`2` is required), so a forwarding
   node on an RA underlay loses its IPv6 default route when the RA lifetime
   expires.
2. **Derived addresses overlap real networks.** Stable addresses hash into
   `192.168.0.0/16` (common home LANs); transfer /31s come from
   `100.64.0.0/10` (CGNAT and Tailscale). Nothing asserts underlay/overlay
   disjointness, and every VM test pins addresses, so the defaults are
   untested.
3. **Birthday collisions.** Ports are `base + hash mod 10000`: a spine with
   50 leaves has about an 11% chance of a collision, 100 leaves about 39%.
   The port range overlaps the kernel ephemeral range `32768–60999`.
4. **One endpoint string per machine.** Private-vs-public endpoint choice
   needs per-adjacency overrides; address family is not modeled, so an
   IPv6-only node and an IPv4-only CGNAT node pass eval and never handshake.
5. **Path MTU is per path, not per node.** GCP is 1460, AWS VPC 9001, the
   Internet 1500 or less; DHCP-learned MTU never reaches the WG MTU.
6. **Reverse-path filtering differs by node type.** Kubernetes nodes use
   loose rpfilter; other fabric nodes keep the NixOS strict default.

### netif

- Physical links require a kernel interface name, which differs per cloud
  and instance type; no MAC matching.
- A missing NIC yields a partial IfState apply; no test proves activation
  fails loudly.
- No cross-instance checks for policy tables, rule priorities or
  overlapping static routes.
- The DHCP route ignore uses `proto 4`; verify which protocol dhcpcd stamps.
- DHCPv6, prefix delegation, DHCP option 121 and option 26 are unexercised.

### routed-fabric

- Source-return tables are `200 + asn mod 40000`: one can land on 200
  (flushed by Cilium) or collide with a netif table.
- FRR default BFD timers (300 ms × 3) on every adjacency, including
  intercontinental and residential links.
- `maximum-prefix 4096` without restart leaves a session down after an
  overflow.
- Border accepts only owned prefixes upstream, so NAT egress cannot be
  expressed today.
- Pod egress to a non-Kubernetes member: masquerade source selection on WG
  devices with only scope-link addresses is untested.

### wireguard-mesh

- Only a mesh-wide "at least one endpoint" check; two NAT'd members never
  connect and VXLAN between them blackholes.
- Overlapping `extraAllowedIPs` between peers silently shadow each other.
- The fixed listen port is not checked against routed-fabric ports on the
  same host.

## Proposed contract additions

| ID | Clause | Enforced by |
| --- | --- | --- |
| U1 Underlay requirements | per adjacency: a shared reachable address family, UDP to the allocated port, path MTU ≥ 1280 + overhead; no L2, multicast or provider anti-spoofing changes | eval (facts), cloud smoke test |
| U2 Address-plan disjointness | underlay prefixes never overlap stable, transfer, pod, Service or pool prefixes | eval |
| U3 Reachability matrix | every adjacency has an endpoint in a shared family and scope; NAT-to-NAT is rejected on both transports | eval, VM negatives |
| U4 Path MTU per adjacency | WG MTU = min(path MTU) − 96, from facts when links are DHCP | eval, `ping -M do` VM |
| C1 Stable convergence | under the Texas–Helsinki WAN profile (≈130 ms RTT, ±20 ms jitter, ≤ 2% loss, 1–2 s loss bursts) for 30 minutes: zero session flaps and zero FIB changes; a dead path is withdrawn within ≤ 15 s on WAN adjacencies and ≤ 3 s on same-site ones; a recovered path returns only after a hold-down; FRR reload loses nothing | VM with timed probes |
| C2 Live change | any inventory change applied by a NixOS generation switch converges without reboot, keeps the deploy SSH session alive, and leaves `ifstatecli check` clean | VM |
| C3 Restart safety | rebooting any single node restores the identical RIB/FIB | VM |
| S1 Exposure | only WireGuard ports answer on untrusted links; BGP/BFD only on fabric interfaces and declared upstream peers | VM negative scans |
| S2 Isolation | separate fabric instances, non-peered clusters and access levels cannot reach what they are not granted | VM |
| F1 Facts completeness | `clan.networkFacts` plus underlay facts drive the reachability matrix and tf firewall rules | eval |

C1 uses two timer profiles per adjacency: `site` = BFD 300 ms × 3 and
`wan` = BFD 1000 ms × 5 with BGP 10/30 s as a backstop. Equal declared
sites default to `site`, different sites to `wan`, and an explicit symmetric
per-adjacency override wins; upstream border sessions always use `wan`.
Phase 2 chooses FRR 10.7 `neighbor <peer> timers delayopen 5` on both ends
for a fixed recovery hold-down. DelayOpen runs on inbound and outbound
session recovery. [FRR 10.7.1 `bgp_bfd.c`](https://github.com/FRRouting/frr/blob/frr-10.7.1/bgpd/bgp_bfd.c)
starts BFD strict hold-time only with a zero effective BGP hold timer, so
it cannot provide this hold-down. DelayOpen is not exponential damping;
[FRR route dampening](https://docs.frrouting.org/en/stable-10.7/bgp.html#route-flap-dampening)
is discouraged and does not cover IPv6 here, so periodic-flap measurement
stays in the phase-6 WAN soak. Every maximum-prefix clause uses `restart 10`.
Profiled neighbors also render plain `bfd`; site defaults stay implicit and
`use-underlays-nexthop-weight` is explicit to match running-config
serialization. An unchanged reload has an empty dry-run diff, preserves peer
uptimes, and leaves the RIB immediately identical; DelayOpen is not
permission for a reload to reset sessions.

The phase-2 review follow-up gives the shared IfState module a stable key and
moves extra port reservations to `clanServices.networking.reservedPorts`, so
repeated imports cannot duplicate the option or invade clan-core's namespace.
Netif rejects the same kernel/Cilium policy tables as source-return.
`sourceReturnPriority` joins `sourceReturnTable` as an explicit collision
escape. The existing routed-fabric VM derives its loopback fixture from
network facts and checks a wildcard TCP/179 listener alongside negative
underlay exposure; no VM suite is added.

## Allocation with clan vars

Each allocated address, ASN, and adjacency port is generated once, committed
as a public non-deployed var, trimmed and read at eval with `getPublicValue`,
and never recomputed from a machine or instance name. Scripts use Python
`ipaddress` and `secrets`. Shared values are read with `machine = null`;
missing values throw the targeted generation command.

| Generator | Scope | Files (public) | Notes |
| --- | --- | --- | --- |
| `routed-fabric-<inst>-ula` | shared | `ula48` | random RFC 4193 ULA; no validation, so pool edits cannot re-roll IPv6 |
| `routed-fabric-<inst>-prefixes` | shared | `loopback4-pool`, `transfer4-pool` | pools default to `198.18.0.0/17` and `198.19.0.0/16`; member settings feed string-only validation and must match the committed records |
| `routed-fabric-<inst>-node` | per machine | `ipv4`, `ipv6` | depends on ULA and prefixes; random host in loopback pool or ULA `:0::/64` |
| `routed-fabric-<inst>-asn` | per machine | `asn` | independent random ASN in 4200000000..4294967294 |
| `routed-fabric-<inst>-adj-<hash>` | shared, one per canonical adjacency key | `port`, `transfer4`, `transfer6` | byte-identical on both endpoints; port from `portRange` (default 10000–29999), transfer /31 from the pool and /127 from ULA `:1::/64` |
| `wireguard-mesh-<inst>-ula` | shared | `ula48` | independent of pool validation |
| `wireguard-mesh-<inst>-prefixes` | shared | `ipv4-pool` | pool defaults to `198.18.128.0/17`, disjoint from routed-fabric loopbacks |
| `wireguard-mesh-<inst>-node` | per machine | `ipv4`, `ipv6` | depends on mesh ULA and prefixes |

Explicit `ipv4`/`ipv6` and per-adjacency `port` settings remain overrides.
Interface names, FRR symbols, link-local addresses, Cilium cluster ids,
Cilium/fallback host ASNs, and pod/service CIDRs remain hash-derived by design.
A generator sees only its dependencies, so uniqueness is enforced by eval
assertions plus a targeted `--regenerate` on the newer machine; never one
allocator per instance (membership changes would renumber everyone). Vars must
exist before eval, and renaming a machine creates a new identity with new vars.
Orphaned adjacency vars need a cleanup check against exported generator names.
Eval also checks allocated-value pool membership, settings/record drift,
cross-instance and cross-service pools on each host, Cilium/host ASN equality,
and reserved/NodePort range overlap. Source-return collisions use their pins.

Collisions are resolved once, then committed values stay stable. For `k`
picks among `N` slots, `P(any collision) ≈ 1 − exp(−k(k−1)/2N)`: 102
loopbacks in a /17 collide with about 15% probability; 100 adjacencies on one
spine have about 22% port (20000 slots) and 14% transfer-/31 collision
probabilities. Eval also rejects unequal pools and overlap with member
underlay or cluster CIDRs. Duplicate transfer prefixes on unrelated hosts are
valid. Regenerating a ULA deliberately renumbers every IPv6 loopback and
transfer in that instance.

## OpenTofu workflow

```
inventory.nix (literal intent)
  -> clan vars generate (allocations, keys)
  -> nix build .#tf-<env> (terranix: machines, sites, sizes, arch, WG ports
     and firewall rules read straight from the clan eval) -> config.tf.json
  -> tofu apply (Nix-pinned providers)
  -> facts.json (public IPs, subnets, MTU, MACs, IPv6; schema-validated)
  -> materialize (pure Nix) -> inventory.<env>.nix (full literal, not committed)
  -> clan machines install (nixos-anywhere)
  -> smoke probes from expected.json
  -> tofu destroy
```

The QEMU harness emits the same `facts.json`, so the schema and materializer
are exercised on every VM run.

| Value | Decided by | Flow |
| --- | --- | --- |
| machine names, roles, sites, sizes, arch | inventory | inventory → terranix → tf |
| private IPs and subnets | inventory | inventory → terranix → tf |
| WireGuard ports and cloud firewall rules | allocated vars | vars → terranix → tf |
| public IPv4, provider IPv6 | provider | tf → facts → inventory |
| MACs, path MTU, NAT, CPU arch | provider and image | tf → facts |
| disk device, boot mode | provider and instance type | tf → facts → disko/facter |

Runs are ephemeral: each works in a throwaway directory outside the repo
(copied clan, per-run age key, fresh vars), keeps state in the Hetzner S3
bucket under its run id with locking, labels every resource with an expiry
(4 h default, 24 h maximum), and ends with `tofu destroy`; a janitor removes
anything expired. Only inputs are committed: `tests/clans/` and `tf/`.
Modules are terranix (Nix) modules, not HCL modules: `hcloud-node`,
`gcp-node`, `proxmox-node` (`bpg/proxmox` provider, tf-chosen MACs),
`baremetal` (reads a hand-written facts stub), later `aws-node` and
`azure-node`.

### Terranix

[terranix](https://github.com/terranix/terranix) evaluates NixOS-style
modules into a Terraform JSON file (`config.tf.json`) that OpenTofu reads
unchanged. It fits this workflow well:

- **One source of truth.** The env module imports the clan's evaluated
  inventory and allocated vars directly, so machine lists, sizes,
  architectures, WireGuard ports and firewall rules never pass through a
  hand-maintained `plan.json` or tf variables.
- **Modules instead of HCL.** `hcloud-node`, `gcp-node` and
  `proxmox-node` become Nix functions with typed options; envs are
  `tests/clans/<name>` plus a provider map.
- **Pinned providers.** `opentofu.withPlugins` pins the hcloud, google and
  bpg/proxmox providers through nixpkgs, so `tofu init` downloads nothing
  and runs are reproducible.
- **Outputs stay tf.** `tofu output -json` still produces `facts.json`; the
  return path (tf → facts → materializer) does not change.

Costs: provider resources are untyped attribute sets (typos surface at
`tofu plan`, not at eval), upstream examples are HCL and must be translated,
and errors point at generated JSON. Mitigations: a `tofu validate` check on
every generated env, and a few typed wrapper options for the fields we
actually use.

How to wire it: add `terranix` to the existing `dev` partition's
`dev/flake.nix` (see [Flake inputs](#flake-inputs)); the tf modules live in
`tf/` and are imported from `dev/flake-module.nix`. A separate `tf`
partition does not work while `partitionedAttrs` routes `apps`, `checks`
and `packages` to `dev`, and a subflake cannot use `follows` to inherit the
parent flake's inputs. The dev partition exposes `packages.<system>.tf-<env>` (via
`terranix.lib.terranixConfiguration`) plus an `apps.<system>.tf-run` wrapper
that writes `config.tf.json` into the throwaway run directory and calls
`tofu`. Recommendation: adopt it in phase 8; it costs one dev-only input and
removes the `plan.json` step.
